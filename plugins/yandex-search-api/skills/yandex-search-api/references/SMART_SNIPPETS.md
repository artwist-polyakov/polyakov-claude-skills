# Smart snippets

Справочник по содержательным выдержкам Yandex Search API: что это, чем
ограничено, как устроено в скилле и как чинить, когда выдержек нет.

## Что это

Обычная выдача даёт ссылку, заголовок и сниппет в одно-два предложения — этого
хватает человеку, который пойдёт на страницу сам, и почти всегда не хватает
агенту, которому надо ответить на вопрос здесь и сейчас.

Smart snippets отдают вместе с каждой ссылкой подготовленный кусок страницы:
достаточно большой, чтобы на нём можно было построить ответ, и достаточно
маленький, чтобы не тащить в контекст всю страницу.

Ключевое свойство: **это оригинальный текст страницы, а не пересказ модели.**
Выдержку можно цитировать как есть и ссылаться на источник — ничего не
дописано и не переформулировано.

## Ограничения

| Что | Значение |
|---|---|
| Режим API | только синхронный (`POST /v2/web/search`) |
| Документов с выдержками | до 20 на запрос |
| Размер выдержки | до 2048 токенов на документ |
| Доступность | не у каждой страницы: зависит от того, открыта ли она и как размечена |

Асинхронный `POST /v2/web/searchAsync` выдержек не возвращает. `web_search_async.sh`
предупреждает об этом на старте и уходит за обычной выдачей — так и задумано,
батч на сотни запросов остаётся асинхронным.

Из «до 20 документов» следует потолок на число результатов: вместе со snippets
`--results` обрезается до 20, а без них работает как раньше.

## Как это включено в скилле

Включено по умолчанию. Выключается тремя способами, от разового к постоянному:

```bash
# разово
bash scripts/web_search_sync.sh --query "..." --no-snippets
```

```jsonc
// config/config.json — насовсем
"search": {
  "smart_snippets": {
    "enabled": false,
    "docs": 20
  }
}
```

`docs` — сколько документов просить с выдержками по умолчанию (1–20). Явный
`--results N` его перекрывает.

## Протокол

Имена из протокола собраны в одном месте — в начале `scripts/common.sh`:

```sh
SMART_SNIPPETS_FLAG_KEY=...    # ключ в metadata.fields запроса
SMART_SNIPPETS_FLAG_VALUE=...  # его значение
SMART_SNIPPETS_XML_TAG=...     # тег с выдержкой внутри <doc> в XML-ответе
```

Флаг уезжает в `metadata.fields` — это map `key:value` из `WebSearchRequest`,
штатный способ включать флаги поиска, не меняя схему запроса:

```json
{
  "query": { "queryText": "...", "searchType": "SEARCH_TYPE_RU" },
  "groupSpec": { "groupMode": "GROUP_MODE_FLAT", "groupsOnPage": 20, "docsInGroup": 1 },
  "region": "213",
  "folderId": "b1g...",
  "metadata": { "fields": { "<SMART_SNIPPETS_FLAG_KEY>": "<SMART_SNIPPETS_FLAG_VALUE>" } }
}
```

Ответ приходит в `rawData` base64 → XML. Парсер ищет `SMART_SNIPPETS_XML_TAG`
внутри каждого `<doc>`; если тегов несколько, их тексты склеиваются через пустую
строку. Не нашёл — `extract` остаётся пустой строкой, и документ честно
помечается в паке как «выдержка недоступна».

Так что при смене протокола правятся три строки, а не пять скриптов.

## Что получается на выходе

Один поиск оставляет в `cache/results/` три файла:

| Файл | Что внутри | Кому |
|---|---|---|
| `<hash>.md` | пак: заголовок, URL и выдержка по каждому документу | агенту — читать |
| `<hash>.json` | то же структурно: `position`, `url`, `title`, `domain`, `snippet`, `extract` | коду — обрабатывать |
| `<hash>.raw` | исходный XML от API | разбору полётов |

`<hash>` — первые 12 символов md5 от текста запроса, так что повторный поиск
той же фразы перезапишет те же файлы.

## Гигиена контекста

20 выдержек по 2048 токенов — это порядка 40 тысяч токенов. Столько нельзя
печатать в stdout: у песочницы жёсткий лимит вывода, и при его превышении
скрипт падает молча — «Error running command» без текста и без stderr.

Поэтому тексты всегда уходят в файл, а в stdout идёт только индекс: строка на
документ с позицией, доменом, размером выдержки и заголовком. В батче
(`--file`) на весь запрос печатается одна строка — иначе десять запросов
упрутся в тот же лимит.

Дальше выбор за агентом:

- нужен один источник — `Read` пака со смещением или `grep` по нему;
- нужны все — `Read` пака целиком, осознавая, что это десятки тысяч токенов;
- нужна структура — `<hash>.json`.

Повторный поиск той же фразы ради текста, который уже лежит в паке, — потраченные
деньги и время.

## Отладка

```bash
# показать тело запроса и выйти, ничего не оплачивая
YSA_DRY_RUN=1 bash scripts/web_search_sync.sh --query "тест"
```

Полезно, чтобы убедиться: флаг в `metadata.fields` действительно уехал, а
`groupsOnPage` равен тому, чего ты ждёшь.

```bash
# офлайн-тесты: ни сети, ни сервисного аккаунта
sh scripts/tests/run.sh
```

Тесты гоняют разбор XML, сборку тела запроса, отрисовку пака и разбор флагов
CLI на фикстурах из `scripts/tests/fixtures/`.

## Когда выдержек нет

| Симптом | Причина | Что делать |
|---|---|---|
| `с выдержками: 0`, поиск отработал | флаг не включён для каталога | проверить, что фича подключена к твоему folder_id |
| `с выдержками: 3` из 20 | часть страниц закрыта или плохо размечена | нормально, пользуйся тем, что пришло |
| выдержек нет в батче | запускался `web_search_async.sh` | повторить через `web_search_sync.sh --file` |
| ошибка 403 | у сервисного аккаунта нет роли | `search-api.webSearch.user`, см. `config/README.md` |
| пустой stdout, «Error running command» | вывод превысил буфер песочницы | уменьшить `--results`, читать пак файлом |

Проверить, что именно вернул API, всегда можно по `<hash>.raw`.

## Цены

Выдержки — это дополнительная работа на стороне API, и тарифицируются они не так,
как голая выдача. Актуальный прайс: https://yandex.cloud/ru/docs/search-api/pricing

Практическое следствие: если задача — снять позиции по сотне запросов, выдержки
не нужны, бери `--no-snippets` или асинхронный режим.
