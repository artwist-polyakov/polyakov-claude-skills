# Состояние и сопровождение сделки

## Начало работы

Храни каждую сделку в отдельной папке пользователя: `deal-state.json`, `documents/`, `creative/`, `evidence/`, `plans/`. При поручении сопровождать сделку создай состояние через `deal.py init` уже при первом обращении, даже если дата и реквизиты неизвестны. Это рабочие материалы пользователя, а не содержимое устанавливаемого навыка. При каждом продолжении сначала прочитай состояние и новые свидетельства. Приватные договоры, переписки, реквизиты и сканы не добавляй в репозиторий навыка.

Для реальной сделки используй обычный `init`; при явно заданном учебном времени сразу передай время и точную фразу пользователя. Выбери одну команду:

```sh
uv run scripts/deal.py init --output "$WORK/deal-state.json"
# Либо учебная сцена; подставь время и фразу из её условия:
uv run scripts/deal.py init --output "$WORK/deal-state.json" --scene-at '2026-11-10T15:00:00+03:00' --scene-source 'Первое сообщение пользователя: «В нашей сцене 10 ноября 2026 года, 15:00 МСК»'
```

Сразу после создания состояния, до подготовки первого ответа, сохрани прямые поручения через `handoff.py instruction` по [порядку выдачи](handoff.md#поручения). Состояние фиксирует известное, а не разрешает публикацию. Разовая бухгалтерская задача использует собственные данные; отдельный учебный пример не меняет основную сделку.

`deal-state.json` — источник состояния; `plan.md` — производный обзор сроков. Для разных документов используются отдельные карты данных: `contract-fields.json` и `accounting.json`. Сверяй совпадающие суммы, стороны, даты, номер договора и НДС до выдачи пакета.

Команда `init` выдаёт уникальный `deal_id`; сохраняй его неизменным всю сделку. При ручном копировании анкеты обязательно назначь новый уникальный ID, не оставляй `new-deal` и не копируй ID другой сделки: на нём основаны идентификаторы календарных событий.

## Время учебной сцены

Если пользователь явно задал учебное время, `init --scene-at … --scene-source …` сохраняет его в необязательном `clock`. Источник — обозначение сообщения пользователя и его точная фраза о времени; наличие отдельного файла не требуется. Схема:

```json
{"clock": {"mode": "scenario", "entries": [
  {"at": "2026-11-10T15:00:00+03:00", "source": "Первое сообщение пользователя: «В нашей сцене 10 ноября 2026 года, 15:00 МСК»"}
]}}
```

Последняя запись задаёт текущее время для `plan`, `check`, импорта, согласования и пересмотра действий. Без `--now` команды используют её; несовпадающий `--now` или `generated_at` выдаваемого плана вызывает отказ. Равные моменты с разными смещениями часового пояса допустимы. Если новая реплика не задаёт нового времени, ничего не меняй. При явно сообщённом новом времени добавь запись:

```sh
uv run scripts/deal.py set-scene-time --state "$WORK/deal-state.json" --at '2026-11-12T18:20:00+03:00' --source 'Новая реплика пользователя: «Сегодня в сцене 12 ноября, 18:20 МСК»'
```

Этой же командой можно привязать старое учебное состояние без `clock` к уже известному времени. Команда сохраняет прежние записи; повтор того же момента не переписывает источник. `history[].scene_at` должен совпадать с одним из сохранённых времён, поэтому прежняя история остаётся допустимой после обновления. Исторические выданные планы не пересчитываются по новому времени. Дата исследования `observed_at`, технические даты файлов и XML не продвигают сцену. Скрипт проверяет согласованность записей, а смысл нового источника проверь по сообщению пользователя; источник нельзя придумывать ради смены времени.

Без `clock` старые состояния и реальные сделки сохраняют прежнее поведение: `--now` задаётся явно либо используются часы компьютера.

## Этапы

| stage | Что должно быть установлено | Следующее действие |
|---|---|---|
| inquiry | Роль, продукт, площадка, запрос | Проверить применимость, собрать недостающие условия |
| terms | Коммерческие условия и роли участников согласованы | Подготовить или проверить договор, счёт и план |
| creative | Утверждены текст, ссылки, медиа | Регистрация в ОРД ответственным участником |
| ready | Доказаны условия публикации | Повторная проверка точной версии и даты |
| published | Есть фактическое время, URL, доказательство выхода | Статистика, окончание размещения, приёмка |
| closing | Услуга завершена, документы подготовлены | Подписать/передать установленным способом, отчётность ОРД |
| closed | Завершены обязательства сторон и применимые отчёты/отчисления | Архивировать подтверждения |
| paused / cancelled | Зафиксированы причина, финансовые последствия, договорённость | Перенести/отменить связанные напоминания, не стирать историю |

Этап меняет агент после проверки фактов. Скрипт не делает переход на основании одной галочки и не подтверждает внешние системы.

При `paused`, `cancelled` или `closed` план снимает активные встроенные напоминания о подготовке креатива, получении ERID, готовности и публикации. Если `publication.actual_at` отсутствует, снимаются также последующие действия размещения и месячный контроль ОРД по плановому интервалу. Если фактический выход уже сохранён, последующие действия и ОРД остаются. Выполненные события сохраняются в `completed`; смена этапа не подтверждает выполнение. Финансовые обязательства, ЭДО и явно внесённые `reporting_deadlines` сохраняются — пересмотри ручные действия отдельно. Возврат к активному этапу восстанавливает встроенные события с прежними UID; увеличь `revision` и проверь `changes` относительно последнего выданного плана.

## Записи и подтверждения

В `checks` для `legality`, `contract`, `payment` (либо `payment_terms`), `creative_approval`, `marking`, `erid`, `ord_creative` сохраняются:

```json
{
  "status": "confirmed",
  "source": "evidence/2026-11-01-confirmation.pdf",
  "checked_at": "2026-11-01T12:00:00+03:00"
}
```

`source` может быть ссылкой, файлом или точной ссылкой на подтверждение пользователя. Не помечай `confirmed` без чтения свидетельства. Платёжное поручение доказывает отправку, а получение оплаты — выписка/подтверждение получателя. Приглашение в ЭДО не означает подписанный договор. Скриншот токена не доказывает остальные условия сделки.

Для проверки реестра ФНС сохрани сам результат запроса: выписку, ответ сервиса или снимок найденной записи с датой. Главная страница реестра и совпадение реквизитов в двух присланных файлах не доказывают проверку по реестру. Если результат получить не удалось, пиши «реквизиты сопоставлены, реестр не проверен», а не «проверил ФНС».

В новой схеме `creative` содержит текст материала, упорядоченную карту якорей и URL, совместимый список адресов и SHA-256 файлов медиа — **без конкретного ERID**. Это версия для согласования и регистрации. Готовая публикация состоит из этого материала и маркировки; её проверяй отдельно, не импортируй вместо материала.

**Действующее подписанное приложение прежней схемы.** Если ERID входит в закреплённый им текст или URL поста, сохраняй соответствующий дословный импорт с ERID. Не снимай актуальность документа и не вырезай маркировку ради перехода или прохождения проверки. Для перехода согласуй изменение подписанных условий и заменяющую редакцию приложения; затем выполни обычный импорт новой версии и сверку действующего комплекта. Отдельное уведомление без изменения приложения применимо, когда в подписанном приложении ERID уже отделён от материала и стороны предусмотрели такой порядок.

В `creative_approval`, `marking`, `erid`, `ord_creative` записывается `creative_sha256` из `deal.py fingerprint`. Выдача токена и имя ОРД хранятся в `checks.erid`, принадлежность зарегистрированному материалу — в `checks.ord_creative`. В `checks.marking` сохраняй тот же `token` и источник проверки фактического способа его вставки в подготовленное сообщение. В `erir` при усиленной политике — тот же `token` и подтверждение проверки. Получение или замена токена не меняет `creative_sha256` и не требует повторного согласования неизменного материала; нужно заново проверить выдачу, принадлежность и маркировку.

Полный `creative_sha256`, включая записи истории, бери только из `import-creative`/`fingerprint`. SHA отдельного исходника называй `text_sha256` или `links_sha256`: эти значения не заменяют хеш всей версии.

Полученные текст и карту ссылок сохраняй дословно и неизменно. Если в них уже есть конкретный ERID, по поручению пользователя или предусмотренному сторонами порядку создай отдельные файлы материала без его строки/параметра. Перед удалением прочитай точный фрагмент и установи его назначение: не очищай текст общей регуляркой и не удаляй все похожие коды. В истории состояния запиши исходные и полученные пути, точное изменение и основание. Сохрани остальные символы, пробелы, якоря и параметры URL, включая UTM. Такой перенос по поручению пользователя отделяет маркировку от содержания; он не даёт права менять смысл текста или приписывать второй стороне согласование, которого нет в источниках. Без соответствующего основания подготовленная версия остаётся предложением.

Для выбранных файлов материала используй `deal.py import-creative --state … --text … --links …`. В `--links` передай **сам выбранный JSON-файл карты**, не переписывай карту в отдельный список URL. Если из карты ничего не выносили, это исходный файл заказчика. Принимаются список URL, список объектов `{"anchor":"…","url":"https://…"}` или таблица `[номер, якорь, адрес]` / `[якорь, адрес]` с необязательным заголовком. Если в ячейке якоря стоит отдельный видимый URL, а рядом только пояснение, адрес берётся из якоря. Неоднозначная строка вызывает отказ до изменения состояния: уточни её, сохраняя оригинал, вместо догадки или сортировки. Повторы, параметры, порядок строк и подписи сохраняются буквально.

Команда сохраняет выбранный файл целиком в `creative.provenance.links`, рабочие пары — в `creative.link_map`, а совместимый список адресов — в `creative.links`. Полный `creative_sha256` после нового импорта учитывает и якоря; прежние состояния без карты сохраняют прежний алгоритм до нового импорта. `fingerprint`, `check` и `plan` сравнивают пары и адреса с исходником. Для приложения передай **тот же файл** в `render_contract.py --links-file …`: `LINK_COUNT` и все `LINK_<N>_ANCHOR/URL` заполнятся автоматически. Противоречащие ручные поля отклоняются. `inspect_links.py --expected …` принимает этот же исходный файл. Не заменяй якорь URL и не группируй повторные адреса.

При смене текста, якоря, адреса, порядка ссылок или медиа повторный импорт переводит в `pending` проверки `creative_approval`, `erid`, `ord_creative`, `marking`, `legality` и `scheduled_message`. Для новой версии заново проверь рекламные заявления и ограничения, затем фактически подготовленный пост или отсутствие отложенного дубля. Оплата, подписанные документы и известный ID отложенного сообщения сохраняются; сам ID не доказывает, что в очереди стоит новая версия. Повторный импорт неизменной версии сохраняет актуальные подтверждения. Не удаляй происхождение и не пересчитывай его вручную для обхода проверки. Импорт сам по себе не подтверждает согласование: сопоставь сообщение пользователя с точной версией и только затем запиши подтверждение.

При переходе от старого импорта с ERID к отдельному материалу без него обычный импорт вычислит новый хеш и снимет прежние подтверждения. Не обходи это ручной правкой SHA или статусов: основание подтверждения выбранного материала установи по исходному согласованию и поручению о переносе, затем используй `approve-creative`. Сам факт переноса не доказывает согласование сторон. В дальнейшем сведения о токене обновляй в проверках без переимпорта материала.

Предложенные смысловые или редакторские правки храни отдельной версией со статусом «на согласовании». Изменение текста, включая пробелы, медиа, якорей, порядка и остальных параметров ссылок требует нового импорта и подтверждения этой версии. Уточни у ОРД, нужна ли новая регистрация при таком изменении; не обещай новый токен при любой опечатке автоматически.

Если сообщение пользователя подтверждает уже импортированную версию, выполни:

```sh
uv run scripts/deal.py approve-creative --state "$WORK/deal-state.json" \
  --source "$WORK/user-message.txt" --quote 'Точная цитата согласования этой версии' \
  --now '2026-11-10T15:00:00+03:00'
```

Подставь реальный источник, дословную цитату и текущее время работы со сделкой (в учебной сцене — её время). Команда проверяет наличие цитаты, сохраняет неизменяемую копию сообщения и SHA, подтверждает только `creative_approval` с полным хешем версии. Смысл цитаты и её отношение к тексту/ссылкам/медиа устанавливает агент; наличие строки само по себе не доказывает согласование. Время фиксации подтверждения не выдаётся за дату первого согласования. ERID, полная версия ОРД, маркировка и готовность публикации проверяются независимо. Спор о токене не повод оставить одобрение неизменного текста в `pending` или включить повторное согласование в план.

Повторное согласование того же полного хеша возвращает `changed=false`: прежние источник, время, история и файлы сохраняются. Это предотвращает лишнее изменение `completed_at` и `SEQUENCE` уже выполненного действия при новом чтении старого поста. Не меняй доказательство вручную ради свежей даты и не копируй техническую запись `approve_creative` второй раз: точный дубль проверка отклонит, сохранив оригинал для исправления. Отмена согласования или исправление установленной ошибки требуют отдельного основания в истории; для новой версии нужен новый импорт и её подтверждение.

Проверка `marking` относится к фактически подготовленному сообщению, с текущим ERID. При получении или замене токена проверь сообщение и обнови подтверждение `marking`, даже если материал не изменился. Добавление параметра `erid` в публикацию не должно менять остальные параметры ссылки; добавление строки ERID — остальной текст. `check` сравнивает записи; он не распознаёт по виду строки, токен ли это.

Снимок поля «Токен» может закрыть выдачу в `checks.erid`, но не сверку материала. В отдельном `checks.ord_creative` сохраняй `status`, `source`, `checked_at`, тот же `token`, актуальный `creative_sha256` и `verified: {"text": false, "links": false, "media": false}`. Каждое значение становится `true` только после чтения соответствующих сведений из ОРД; отсутствие медиа тоже нужно сверить. Пока полный текст или список URL скрыт, проверка остаётся `pending`. Подробности и допустимые источники — в [справке ОРД](ord-edo.md). Свой пост, приложение и его хеш не являются выгрузкой ОРД. `check` отдельно требует обе проверки, а изменение креатива снимает обе. При обновлении старого состояния добавь новую проверку как незавершённую; не переноси прежнее `erid=confirmed` автоматически.

`commercial.contract_author` означает автора/сторону подготовки договора, а не автора рекламного поста. Эти роли могут различаться; неизвестное оставляй `null`.

Учёт файлов в `documents` и дословных поручений в `user_instructions` веди по [порядку выдачи](handoff.md): используй `handoff.py register` и `handoff.py instruction`, не дублируй их ручным реестром или пересчётом SHA. До каждого ответа зарегистрируй все выдаваемые файлы, включая первоначальные проекты, PDF-превью, сверку, правки, план и ICS; черновик ответа проверяй через `handoff.py check`. Регистрация не подтверждает подпись или принятие условий. При замене используй `--supersedes`: факт прежней выдачи сохраняется отдельно от актуальности.

Последний шаг перед передачей готового окончательного ответа пользователю обязателен: `uv run scripts/handoff.py check --state "$WORK/deal-state.json" --response "$WORK/reply.txt" --record-issue`. Только при успешной проверке флаг фиксирует в `state.plan_issues` пути и SHA текущего плана и ответа. Для внутренних черновиков используй обычный `check`: он и `register` не фиксируют выдачу плана. Запись `--record-issue` не означает установку внешних напоминаний или отправку документов контрагенту.

В `history` сохраняй дату, изменение и основание; собственные советы и выводы — здесь или в `recommendations`. Вопрос пользователя, факт сделки и фраза из чужого примера не становятся поручением. При `documents_human_only` предложи правки отдельным текстом. При обычном редактировании сохраняй исходник и новую версию; не собирай поверх ручных изменений.

Полученный скан проверяй по документам и сторонам, а не по имени файла. Для основного договора и каждого приложения:

1. Найди страницу с подписями и увеличь участок, включающий заголовки обеих сторон, линии подписей и расшифровки. Сохрани этот участок в `evidence/`.
2. Для каждой стороны отдельно запиши документ, страницу, роль, наличие видимого росчерка и путь к изображению. Пустая линия с напечатанным Ф. И. О. означает, что в этой копии подпись не подтверждена; подпись одной стороны не подтверждает другую.
3. При нечитаемом изображении запиши «не установлено», а не «подписано». Видимый росчерк не доказывает подлинность, полномочия или дату подписания; эти вопросы проверяются отдельно при необходимости.
4. Перед ответом сверь каждое утверждение «подписан обеими сторонами» с двумя отдельными наблюдениями. Новый проект или дополнительное соглашение не наследует подписи из прежнего файла.

Отсутствие подписи в конкретном скане не доказывает отсутствие другого подписанного экземпляра или дату любого подписания человеком. Пока таких сведений нет, пиши «в полученном пакете подпись не подтверждена; дата неизвестна». Даже при известной дате оплаты нельзя утверждать «оплата была до подписи» без даты подписания. Не включай признание нарушения на основании одного скана.

Выбранный пользователем чат для сканов сохраняется как способ обмена. Наличие email в карточке не означает согласия перенести обмен в почту. Если не хватает идентификатора отправителя в выбранном чате, отметь это как недостающее поле, не меняя канал связи.

При новых подтверждениях пересмотри прежние выводы: полученная оплата не должна сосуществовать с действующим ограничением «оплата отсутствует». Историю при этом сохраняй, а текущий статус обновляй.

Подтверждение поступления хранится в `checks.payment`; не создавай второй флаг `commercial.payment_received`. При обновлении старого состояния перенеси его источник в единственную проверку и убери дублирующий флаг, сохранив сумму, дату поступления и историю изменения. Для каждого нового существенного факта запиши в истории время фиксации и источник; дата фиксации не подменяет фактическую дату события.

До изменения состояния и расписания по полученной редакции выполни [сверку условий](contract-review.md): заполни один JSON решений с цитатами, страницами и статусами согласования. `review.py build` создаёт из него таблицу и лист конкретных правок в отдельном каталоге `documents/review-vN/`; `review.py audit` проверяет их согласованность. Не составляй эти файлы независимо и не правь результаты вручную: измени решение и собери новую версию. Для `replace/append` нужен готовый текст, для отложенного решения — `defer` с причиной. Прочитай итоговые файлы и сопоставь их с решениями; проверка скрипта не доказывает точность цитаты или смысла правки.

Подписи и содержание проверяются независимо: неподписанность не отменяет извлечённые условия. Для каждого выбранного значения укажи пункт, статус согласования и решение; в истории состояния сохрани ссылку на сгенерированную таблицу. Прежний проект агента не заменяет чтение полученного документа. После сверки обнови состояние и план; выдаваемые результаты зарегистрируй по порядку выше.

## Готовность к публикации

Готовность требует подтверждённых законности, подписания нужных документов, окончательного креатива, маркировки, выдачи ERID, полного материала ОРД, выполнения условий оплаты и текущей очереди. Предоплата и обязательное ожидание видимости в ЕРИР зависят от условий/политики, не универсальны. В ответе опирайся на реальные `blockers` и `readiness_policy` из `deal.py check`: при `require_erir_visibility=false` не требуй дождаться статуса ЕРИР. Информационную проверку ЕРИР называй отдельно; она не заменяет выдачу токена и полную сверку материала ОРД. При `true` назови ожидание ЕРИР дополнительным согласованным условием.

`checks.erid` подтверждает выдачу, `checks.ord_creative` — полный текст, все URL и медиа из ОРД: `verified.text/links/media`. Снимок токена, свёрнутые ссылки и своё приложение не закрывают полную сверку. `check` проверяет записи, внешние доказательства читай самостоятельно. Спорные коды разбирай по [справке ОРД и ЭДО](ord-edo.md).

`checks.scheduled_message` обязателен даже при неизвестном ID: после восстановления или повторного создания отложенной записи нужен актуальный просмотр очереди; при ручном выходе — проверка отсутствия отложенного дубля. После просмотра запиши `status=confirmed`, текстовый `source`, `checked_at` и снимок проверенного размещения: `publication_at` из `schedule.publication_at` и `scheduled_message_id` из `publication.scheduled_message_id`. Если отложенная запись существует, также сохрани в подтверждении `token` после проверки ERID в этой записи: пропущенный или устаревший токен требует нового просмотра очереди. Если ID отсутствует, запиши явный `null`; пропущенное поле не означает проверку отсутствия дубля. Подтверждённое отсутствие отложенной записи не зависит от смены ERID; маркировка готового сообщения проверяется отдельно. Перенос на другой момент или изменение ID делает прежнее подтверждение неактуальным даже при прямом редактировании состояния; другой формат даты или смещение при том же моменте времени не считается переносом. Старое подтверждение без обоих полей тоже требует повторного просмотра. До него оставь `pending`: не дополняй старую запись снимком автоматически и не заменяй проверку свободным текстом истории.

При сопровождении сразу после согласования даты размещения подготовь и выдай локальный план JSON/Markdown/ICS вместе с первым пакетом документов. Неизвестные подписи, реквизиты и ERID остаются открытыми действиями, а не поводом пропустить план. Перед ответом синхронизируй все актуальные собственные заметки, поля документов и описания событий с новыми доказательствами. Устаревшие проекты сохраняй историческими; нужные для дальнейшего согласования выпусти актуальной версией по [порядку выбора документов](contract-review.md#актуальность-собственных-проектов).

```sh
uv run scripts/deal.py check --state "$WORK/deal-state.json"
uv run scripts/deal.py plan --state "$WORK/deal-state.json" --output-dir "$WORK/plans/v1"
# Для следующей выдачи: v1 уже зафиксирован как последний выданный план.
uv run scripts/deal.py plan --state "$WORK/deal-state.json" --previous "$WORK/plans/v1/plan.json" --output-dir "$WORK/plans/v2"
```

Коды `deal.py check`: 0 — записи готовы, 2 — подтверждения отсутствуют, 1 — неверные данные. `plan` ничего не устанавливает; техническая проверка выдачи выполняется отдельно по [handoff.md](handoff.md#заключительная-проверка).

## Сроки и напоминания

Перед добавлением ручного события проверь уже создаваемые скриптом действия. При известном `closing_after_end_hours` событие `closing` уже напоминает подготовить закрывающие документы; при заданных дате и часе проверки ЭДО событие `edo-recovery` уже проверяет доступность сервиса. Не дублируй те же действия и сроки в `reporting_deadlines` под другим ID. Отдельное событие уместно для другого результата: например, после восстановления отправить документы и проверить квитанции. Уточнение применимости и периода рекламного сбора называй самостоятельным действием, не маскируй его заголовком об оформлении УПД.

Срок передачи ссылки заказчику хранится в `schedule.link_after_publication_hours`: число часов после фактической публикации, либо `null`, если срок неизвестен. По известному числу создаётся событие `link`; при `null` остаётся предупреждение, время не выдумывается. Если срок считается от другого события или в рабочих днях, сохрани исходное условие и рассчитай отдельное событие. В старых файлах без этого поля сохраняется прежний расчёт +1 час как организационный ориентир, а не подтверждённый договорный срок; при получении нового договора явно обнови поле по его тексту.

Разделяй согласованный срок и выбранное агентом время напоминания. «За один рабочий день» без указанного часа не означает «в час публикации предыдущего рабочего дня». Не дописывай час в договор; неоднозначность отметь и уточни при необходимости. Примеры T−2 и T−24 — организационные ориентиры, пока стороны не сделали их условиями сделки. В `source` отмечай выбранный тобой срок как предложение агента и называй действительное основание (пример навыка, собственный расчёт или другой источник), не приписывая его условиям канала или документам пользователя, где такого срока нет. Отсутствие подтверждения заранее не доказывает просрочку: установи применимый срок и фактическое исполнение. До его истечения показывай, что осталось сделать; перенос предлагай по конкретной причине, не записывай его как согласованный без решения пользователя.

Перед ответом раздели ближайшие даты на договорные и организационные. Нельзя завершать смешанный список общим правилом «не успеем к этим датам — нужно заново согласовать публикацию». Например, подпись и платёж могут иметь согласованный предел, а получение карточки ОРД в четверг — только твой запас времени. При задержке карточки проверь возможность получить и сверить её до применимого предела, а не требуй сменить дату из-за пропущенного четверга. Условия переноса в ответе, плане и договоре должны совпадать; конкретную задержку называй по её фактическому источнику.

Это относится и к `source`/`note` любого организационного события, включая проверку за час до выхода: незакрытое действие требует проверить выполнимость к действительному сроку, а не автоматически согласовывать перенос. Ближайшие действия должны быть в самом плане и ICS. Объяснения выдавай из итогового плана, без параллельной памятки с другими сроками или условиями переноса.

1. Проверь текущее время, точный часовой пояс, согласованную дату и доступные средства: календарь, напоминания, расписание пробуждений агента. Для учебной сцены действует [сохранённое время](#время-учебной-сцены). Для напоминаний о подготовке материалов, ОРД, отчислениях и восстановлении ЭДО местный час в `schedule.timezone` должен существовать и быть однозначным. При переводе часов пропущенное или повторяющееся время отклоняется: выбери другой час проверки, автоматического сдвига нет.
2. До заполнения договора сохрани условие оплаты в `schedule.deadline_terms.payment`: `condition` — исходная формулировка, `source` — сообщение/пункт, `precision` — `unspecified`, `relative`, `date` или `datetime`. `unspecified` означает отсутствие самого условия и требует `condition/source=null`; известное условие и источник сохраняй непустыми строками с подходящей точностью. «За рабочий день» — `relative`, а не `datetime`; `payment_due_at` остаётся `null`. Дата без часа — `date`, также без `payment_due_at`. Только прямо согласованные дата и час дают `datetime` и точный `payment_due_at` со смещением. Аналогично `deadline_terms.erid` и `erid_due_at`. Скрипт отклоняет точные сроки без такого основания; нельзя менять precision только ради прохождения проверки. Напоминание в выбранный час добавляй отдельным событием с пояснением, что это время проверки, а не новый предел обязательства.

   `text_before_business_days` (пример: 2) считается с учётом `holidays` и `working_days`: внеси официальные праздники и перенесённые рабочие дни для затронутого периода. Без `work_calendar_verified` план явно предупреждает об упрощении. Час этого напоминания заимствован из времени выхода для удобства планирования, а не из условия договора. `readiness_before_hours` (пример: 24) задаёт предварительную проверку, не новую обязанность оплатить к её началу.
3. Сроки после публикации считаются от `publication.actual_at`, пока его нет — предварительно от планового времени. `claims_after_end_hours` и `closing_after_end_hours` — только часы после завершения размещения. Это параметры договора, не универсальные законные сроки. У каждого условия установи действие, длительность, единицу и начало отсчёта.

   `closing_after_end_hours` по умолчанию `null`; отсутствующее поле в старом состоянии также означает неизвестный срок. Пока условие не установлено, событие `closing` не создаётся, план предупреждает. «УПД через 48 часов после размещения» может означать после выхода или после окончания услуги: уточни начало отсчёта, не подставляй 48 автоматически. В проекте оставь явное место для согласования. Если установлены 48 часов размещения и ещё 48 часов после его окончания до УПД, явное значение `48` даёт T+96. Условие от начала публикации или другого события сохрани дословно и после расчёта внеси отдельным событием с источником; не маскируй его под часы после окончания.

   Если замечания принимаются в рабочих днях или отсчёт начинается с получения подтверждения, нельзя подставлять приблизительные календарные часы. Укажи `claims_after_end_hours: null`: событие с выдуманным сроком не создаётся, план показывает предупреждение. Добавь отдельную внутреннюю проверку получения подтверждения; после получения рассчитай договорный срок с нужным календарём и внеси его отдельным событием с источником. При неизвестном сроке УПД также можно отдельно назначить организационную проверку, явно назвав её так.

   Если полученная редакция прямо задаёт число часов после окончания размещения, этот срок представим: извлеки число, источник и статус согласования по таблице сверки. Отсутствие подписи само по себе не основание для `null` или вывода «срок неизвестен». Даже предварительный срок в плане должен совпадать с выбранным пунктом по единицам и началу отсчёта.
4. Месячный контроль ОРД рассчитывается автоматически через `schedule.ord_reporting`:

   ```json
   {"applicability": "unknown", "responsible": null, "source": null,
    "distribution_end_at": null, "distribution_end_source": null,
    "reminder_time": "09:00"}
   ```

   `applicability`: `unknown`, `applicable` или `not_applicable` относится к обычному месячному сроку; последние два значения требуют `source`. Укажи ответственного в `responsible` по договорённости, не по роли пользователя, и согласуй с `responsibilities.ord_reporting`. При неизвестной применимости или старом состоянии без этого блока контроль всё равно создаётся, но его дата организационная (`legal_date=null`), а не подтверждённый законный предел. Уточни применимую норму/порядок у ОРД; оговорка о годе после исполнения договора не даёт разрешения отложить первую подачу на год — см. [справку ОРД](ord-edo.md).

   `plan` берёт начало из `publication.actual_at`, иначе из планового времени. Пока `distribution_end_at` не задан, конец предварительно считается по `duration_hours`; это не доказательство удаления поста. При более долгом распространении внеси проверенную границу `distribution_end_at` и её основание `distribution_end_source`. Для продолжающегося поста используй явно обозначенную предварительную границу планирования, периодически проверяй и продлевай её; не закрывай дальнейшую отчётность договорными 48 часами или датой УПД. Конец интервала исключается: размещение до 1 ноября 00:00 не добавляет ноябрь, до 00:01 — добавляет.

   На каждый затронутый месяц создаётся `ord-YYYY-MM`, дата контроля — последний день месяца плюс 30 календарных дней. Например, за январь 2026 года это 02.03, не 28.02 и не 30.03. Источник нормы, месяц, применимость, ответственный и организационный час отражены в событии. Проверяется передача сведений ответственным участником; скрипт ничего не подаёт и не подтверждает фактическую отправку. Заверши каждый месяц отдельно через `completed_events["ord-YYYY-MM"]` только с доказательством передачи; выдача ERID и УПД его не закрывают.

   В `reporting_deadlines` оставляй дополнительные договорные/организационные действия с постоянными уникальными ID: `{ "id": "contract-statistics-oct", "title": "…", "at": "…+03:00", "source": "условие, ответственный и основание выбранного часа" }`. ID `ord-YYYY-MM` зарезервирован: ручной дубль вызывает ошибку, а не молча заменяет более ранний договорный срок. При миграции убери обычный ручной дубль; если это особое договорное действие, сохрани его срок и источник под отдельным ID. Проверь `changes` относительно выданного/установленного плана. Применимость и сроки сверяй по [правовой справке](legal.md); дата УПД их не переносит.

   Квартальные отчисления задавай отдельно в `schedule.fee_obligation`, чтобы не пропустить проверку расчёта до уплаты:

   При известном ожидаемом месяце поступления денег сохрани предварительный квартал и его источник, даже если применимость и законный плательщик ещё неизвестны. Все три условных проверки нужны уже в первом плане. Дата публикации сама по себе не устанавливает квартал дохода: аванс может относиться к другому периоду. Если период действительно нельзя определить, оставь `quarters=[]`. При `applicability=unknown` всегда добавь ближайшее организационное действие с `checks: ["fee_period"]`, чтобы установить применимость, законного плательщика и юридический период дохода, даже если предварительные кварталы уже выбраны. Три квартальные проверки это уточнение не заменяют; без активного действия `plan` отвергает неполный план. После уточнения внеси кварталы/основание либо подтверждённую неприменимость и пересчитай план. Это действие не является дополнительным условием разрешения публикации.

   ```json
   {"applicability": "unknown", "payer": null,
    "source": "Предварительный период 2026-Q4 по договорной дате предоплаты в октябре; поступление, юридический период, применимость и плательщик не подтверждены",
    "quarters": ["2026-Q4"], "reminder_time": "09:00"}
   ```

   `applicability` принимает `unknown`, `applicable`, `not_applicable`. Для установленной применимости нужны `payer` (конкретное лицо), `source` (правовое основание и факты цепочки) и непустой список платёжных кварталов. Для неприменимости тоже нужно основание. Расходы в цене, `user_role` и поручение заказчику маркировать рекламу сами по себе не определяют законного плательщика. Согласуй запись с `responsibilities.fee_legal_payer`.

   После подтверждения оплаты пересмотри `fee_obligation.source`, выбранные кварталы и оставшиеся действия по новым свидетельствам. Отдельно отрази установленное зачисление и ещё не установленные применимость, плательщика или юридический период дохода. Для сохранённого `source` при `checks.payment.status=confirmed` обязательна актуальная `payment_basis_sha256`. Команда `uv run scripts/deal.py fee-payment-basis --state "$WORK/deal-state.json"` только читает состояние и выводит `sha256` и `evidence`; она работает и до исправления устаревшей привязки. Прочитай оба свидетельства, обнови основание, затем сохрани выданный `sha256` в `schedule.fee_obligation.payment_basis_sha256`. Не заменяй пересмотр основания одним новым хешем.

   Привязка охватывает содержимое `checks.payment` и `completed_events.payment`, кроме `checked_at`: повторная сверка того же факта не меняет основание. Изменение суммы, источника, даты события, отзыв подтверждения или удаление свидетельства делают прежнюю привязку недействительной; проверка останавливается до пересмотра основания и действий. Скрипт не выводит квартал дохода из даты оплаты и не назначает плательщика. Известное поступление может сочетаться с предварительным кварталом и открытым правовым вопросом. SHA связывает основание с текущими свидетельствами, но не проверяет правильность его смысла.

   При неизвестной применимости внеси **предварительные кварталы и их основание** до выдачи плана. Скрипт создаст три условные проверки; они не требуют платить, но не дадут впервые открыть ЕРИР лишь в день уплаты. Если при `unknown` кварталы пусты, но договорная дата платежа известна (`payment_due_at` в часовом поясе сделки либо расчёт рабочих дней), скрипт сам создаёт три предварительные проверки по кварталу этой даты. События содержат `period_basis=contractual_payment_deadline` и `payment_due_on`; состояние не изменяется. Это ориентир контроля, **не установленный период дохода**. Неизвестность плательщика не должна удалять эти даты.

   Если ни явных кварталов, ни вычислимой договорной даты платежа нет, три даты пока не создаются — сохрани предупреждение и ближайшее действие выяснить период. Дата проверки оплаты `checked_at`, дата публикации, дата УПД и организационное `uncomputed.review_on` не заменяют дату дохода. Явно заданные кварталы имеют приоритет перед предварительным расчётом.

   По [ПП РФ № 1224, пп. 8, 9, 13, 15](https://publication.pravo.gov.ru/document/0001202508150004) `plan` создаёт `fee-YYYY-QN-assessment` (расчёт РКН к 15-му второго месяца следующего квартала), `fee-YYYY-QN-review` (проверка/уточнение в следующие 10 календарных дней) и `fee-YYYY-QN-payment` (уплата до 5-го третьего месяца). За 2026-Q4 это 15.02, 25.02 и 05.03.2027. `reminder_time` — выбранный организационный час в `schedule.timezone`, **не час из закона**; календарная дата нормы, квартал, источники и применимость записываются отдельно в события и их описания. Расчёт, сумма и УИН берутся из ЕРИР, скрипт их не создаёт. Если утром 15-го расчёта ещё нет, проверь повторно после его формирования. Не дублируй эти три события вручную в `reporting_deadlines`; при переходе со старого плана убери прежние ручные события отчислений, увеличь `revision` и проверь `changes`.

   Для первого платёжного периода 2025-Q2 действовали те же контрольные даты: 15.08, 25.08 и 05.09.2025; они прямо указаны в [сообщении Роскомнадзора](https://t.me/rkn_tg/1547). Отдельный переходный срок для этого периода в расчёт не добавляется.
5. Перед пересчётом плана обнови подтверждения и тексты оставшихся событий по новым доказательствам. Разрешённый конфликт токенов убери из описания, сохранив ещё не выполненную сверку полного материала. `creative_approval` и `payment` с действующими доказательствами автоматически убирают соответствующие напоминания из `events` в `completed`. Для события `erid` нужны обе проверки: выдача `erid` и полная сверка `ord_creative`; одно только поле токена не завершает задачу. Это относится и к дополнительным событиям из `reporting_deadlines`: получение токена может закрыть отдельную задачу выдачи, но напоминание сверить полный материал должно оставаться активным до `ord_creative=confirmed`. Подтверждение текста/ERID действует только для текущего `creative_sha256`: изменённая версия снова требует проверки. Согласование текста и регистрация в ОРД — отдельные события; ожидаемый токен не делает уже согласованный текст несогласованным.

   Остальные выполненные действия укажи в `completed_events` по постоянному ID события, например `{"link": {"status": "confirmed", "source": "сообщение пользователя об отправке", "checked_at": "2026-11-10T10:05:00+03:00"}}`. Для дополнительного события используется полный ID `report-...`, для отчислений — `fee-2026-Q4-assessment`, `fee-2026-Q4-review` или `fee-2026-Q4-payment`. Проверка наличия расчёта не завершает уточнение и уплату; завершай каждый этап только по доказательству именно этого действия. При переходе от предварительного контроля к установленной обязанности пересмотри доказательства завершения. Выполненное действие остаётся в истории и разделе `completed`, не попадает в ICS и не выдаётся за просроченное. В `changes.cancel` попадает прежнее напоминание о нём: это отмена уведомления, не отмена сделки. Неподтверждённые прошедшие напоминания не переносятся молча в будущее; их прошедшее время само по себе не доказывает нарушение договора. При изменении плана увеличь `schedule.revision`. В `--previous` передавай **последний план, реально выданный пользователю или установленный в выбранном канале**, а не промежуточную сборку текущего ответа. Во время нескольких внутренних правок сохраняй одну и ту же базу сравнения: итоговый `changes` должен охватывать все изменения относительно неё. Сохрани путь этой базы в истории и не считай внутреннюю сборку установленной. Если выданный и установленный планы различаются, для обновления интеграции сравнивай с последним подтверждённо установленным в ней планом и явно укажи базу.

   Последняя зафиксированная выдача находится в `state.plan_issues`, запись создаёт заключительный `handoff.py check --record-issue`. Регистрация новой версии и промежуточные успешные проверки не сдвигают эту базу. Для всех пересборок одного ответа используй тот же последний зафиксированный план; `handoff` проверяет SHA базы, состав `changes` и значения `SEQUENCE` относительно неё. Фиксируй новую выдачу только после завершения правок и проверки окончательного ответа.
6. `reminders.ics` содержит события и напоминания, но создание файла не устанавливает их. Если пользователь поручил сопровождение и есть доступный инструмент — создай/обнови события через него. Одного надёжного канала обычно достаточно; несколько — по предпочтению пользователя. При отсутствии интеграции выдай ICS для импорта и прямо укажи, что автоматические уведомления пока не работают.

Перед выдачей плана добавь конкретные ближайшие незавершённые действия, если общая проверка готовности наступает слишком поздно: подпись, сверку зарегистрированного материала, восстановление ЭДО или проверку отложенной записи. Запиши их по формату ниже: отдельная памятка со словами «сделать сейчас» не заменяет события в плане.

7. В `integrations` сохрани канал, внешние идентификаторы, UID события, версию плана и ответ инструмента. При переносе обновляй существующие записи, удаляй/отменяй только относящиеся к этой сделке. Поле `changes` перечисляет создание/изменение/отмену; повторный импорт ICS не у всех календарей предотвращает дубли.
8. Пробуждение агента должно читать состояние сделки, проверять наступившее действие и уведомлять только о требуемом действии, сбое, изменении или завершении. Не создавать новые повторяющиеся задачи при каждом пробуждении. Если среда запрещает создание/изменение расписания, сообщи ограничение и передай пользователю план; не обходи запрет заменой чужой задачи.

## Расчёт относительного срока

У относительного условия оплаты или ERID перед построением плана заполни `calculation`. Исходная формулировка и источник остаются в `deadline_terms`; расчёт нужен для своевременных действий, а не для добавления часа к договору. Для известного количества рабочих дней до публикации:

```json
{
  "precision": "relative",
  "condition": "Полная предоплата после подписания обеими сторонами, не менее чем за один рабочий день до публикации",
  "source": "Сообщение пользователя с согласованным порядком оплаты",
  "calculation": {
    "kind": "business_days_before_publication",
    "days": 1,
    "requires": ["contract"]
  }
}
```

`days` берётся из условия, `requires` — только из явно установленного порядка. Если подписание не является предпосылкой оплаты, не добавляй его автоматически. Для выдачи ERID также не назначай полную сверку ОРД предпосылкой без основания. При этом самостоятельные условия готовности к публикации сохраняются. Используются `holidays` и `working_days`; отсутствие подтверждённого рабочего календаря отражается предупреждением.

Расчёт даёт **календарную дату без часа**. При выходе в понедельник и условии «за один рабочий день» ближайшие действия не должны впервые появляться в субботу. В оставшуюся пятницу нужны проверка выполнимости, согласование недостающих условий, резервный обмен, подписи и оплата в установленном порядке. Если успеть нельзя, предложи конкретное изменение срока или даты для согласования; самостоятельно не меняй договор и не объявляй перенос состоявшимся.

`plan` требует активные действия по самому незавершённому условию и его открытым предпосылкам не позже вычисленного дня. Когда день уже наступил или прошёл, действие нельзя впервые откладывать на завтра. Существующее просроченное напоминание сохраняется с прежним ID, временем и историей; его необходимо выполнить сейчас или явно согласовать изменение. Признак прошедшего напоминания сам по себе не доказывает просрочку обязательства в определённый час. Уже подтверждённая оплата не открывается заново из-за неподписанного документа: подпись проверяется отдельно.

Для другого относительного условия, которое пока нельзя вычислить, используй:

```json
{
  "kind": "uncomputed",
  "reason": "Начало отсчёта — получение отчёта, дата ещё не подтверждена",
  "review_on": "2026-11-10",
  "requires": []
}
```

Это значение `calculation`, а не замена всему условию. `review_on` — выбранный организационный день проверки основания, не договорный срок. Запиши причину и назначь действие на этот день; после получения факта рассчитай срок. Не выбирай эту ветку для обхода известного количества рабочих дней. Известное `relative` без `calculation` не позволяет выдать план; проверка фактов `check` остаётся независимой.

## Покрытие незавершённых действий

`plan` проверяет, что до публикации у каждого незавершённого условия готовности есть активное действие не позже выхода. Учитываются актуальность подтверждения, версия креатива, токен и полнота сверки ОРД. Общая `readiness` и выполненные события покрытием не считаются. Ошибка «План неполон» перечисляет недостающие проверки: добавь организационные действия, сохраняя `unknown/pending` до реального подтверждения. Для построения плана не требуется выдумывать оплату, подпись или ответ внешней системы. `deal.py check` проверяет факты независимо от полноты плана.

Для такого действия используй существующий `schedule.reporting_deadlines`:

```json
{
  "id": "contract-signing",
  "title": "Получить подписанный договор и приложения",
  "at": "2026-11-10T15:00:00+03:00",
  "source": "В полученной редакции подпись не подтверждена; выбран час организационной проверки",
  "kind": "organizational",
  "checks": ["contract"]
}
```

Это пример структуры, не готовый срок для сделки. `checks` — непустой список ключей проверок без повторов: `legality`, `contract`, `creative_approval`, `marking`, `erid`, `ord_creative`, `scheduled_message`, `erir`, `payment`, `payment_terms`, `edo_exchange` или `fee_period`. Соедини несколько проверок в одном событии только когда их выполняет одно конкретное действие, например получение токена и сверка карточки ОРД. В `title` запиши действие, в `source` — основание и точные указания. Для ОРД нужны полный текст, все URL и медиа либо их отсутствие; полученный токен не заменяет сверку.

События `creative`, `payment` и `erid` уже покрывают соответствующие проверки; `erid` включает `ord_creative`. Не создавай их ручные дубли. Если точный договорный час оплаты или передачи токена неизвестен, добавь организационное действие; не заполняй ради календаря `*_due_at` выдуманным сроком. Событие без `kind/checks` остаётся обычным дополнительным сроком и не закрывает пробел покрытия. Для действительно более раннего отдельного действия укажи его цель и основание, сохранив договорный срок.

При ожидании восстановления ЭДО добавь необязательную запись `checks.edo_exchange` со статусом `pending` и источником сбоя, затем действие обмена с `checks: ["edo_exchange"]`. В объявленной записи обязательно поле `recovery_expected_on`: дата, названная в сообщении (`YYYY-MM-DD`), или явное `null`, если дата неизвестна. В `recovery_source` сохраняй ссылку и точную формулировку сообщения. «До <дата>» сохраняется буквально: включительность и обещанный момент восстановления без подтверждения не выводятся.

Выбранный день контроля хранится отдельно в необязательном `recovery_check_on`, час — в `recovery_check_time` (`HH:MM`). Если `recovery_check_on` отсутствует или равен `null`, проверка назначается на `recovery_expected_on`, как в прежнем формате. Отдельный день можно выбрать и при неизвестной дате восстановления; если обе даты неизвестны, событие не создаётся и `recovery_source/recovery_check_time` не заполняются. Например, сообщение «До 5 ноября недоступны приглашения» и решение проверить сервис 6 ноября записываются так:

```json
{
  "recovery_expected_on": "2026-11-05",
  "recovery_source": "messages/operator.txt: До 5 ноября недоступны приглашения",
  "recovery_check_on": "2026-11-06",
  "recovery_check_time": "09:00"
}
```

План создаст отдельное событие `edo-recovery` на выбранные день и час в `schedule.timezone`, показывая дату и формулировку источника отдельно. Выполнение события записывается в `completed_events["edo-recovery"]`; восстановление системы не доказывает отправку, подписание или принятие документов. Не дублируй это событие вручную и не назначай на его дату получение карточки ОРД без отдельного основания: это разные системы. Само ожидание ЭДО не создаёт новое условие разрешения публикации; согласованный резервный обмен и подписание проверяются отдельно. Действие обмена требуется и после выхода, пока он не завершён. При отсутствии такого ожидания запись не нужна.

`at` — точное выбранное время с часовым поясом, сохранённое в состоянии. Повторный запуск с другим `--now` меняет только признак прошедшего напоминания, а не переносит действие. Перенос выполняй явно, сохраняя `id`, основание и историю, увеличивая `revision` и сравнивая с последним выданным планом. Организационный час не является сроком обязательства. Незакрытый пункт в час `readiness` требует уточнить препятствие и действительный срок, а не автоматически переносить публикацию.

При обновлении сначала возьми незавершённые действия из последнего выданного плана и измени их текст/время под прежними ID. Новый текст «проверить текущую очередь» не создаёт новую задачу вместо прежней «проверить очередь». `plan --previous` отвергает удаление незавершённого организационного события одновременно с созданием другого ID для того же набора `checks`: исправь ID в состоянии. Действительно выполненное действие сохраняй в `completed`; простая отмена не требует создания замены.

При пересчёте план сравнивает отпечаток связанных `checks` с последней выданной версией. Если факты изменились, прежний `source` активного действия нельзя переносить молча, даже при новом заголовке: исправь устаревшие сведения под тем же ID и проверь соответствие `title`. Если обе формулировки остаются точными, зафиксируй пересмотр без косметической правки:

```bash
uv run scripts/deal.py review-action --state "$WORK/deal-state.json" --id contract-signing --reason "Реквизиты теперь известны; прежнее действие получить подписи по-прежнему требуется"
```

В учебной сцене время пересмотра берётся из `clock`. Команда связывает пересмотр с конкретным ID, текстом действия и текущими фактами; при следующем изменении подтверждение не переносится. Новое действие или внутренняя версия плана не снимает проверку прежнего. Для плана старой версии без отпечатков нужен однократный пересмотр неизменённых формулировок. Отпечаток исключает `checked_at` и сам по себе не доказывает смысл текста; это проверка пересмотра, а не автоматическая сверка фактов. Служебные отпечатки и записи пересмотра не повышают `SEQUENCE` неизменного календарного события.

Если выполненное действие убрано из `reporting_deadlines`, пересчёт с `--previous` сохраняет его в `completed` по действующему `completed_events` либо, при отсутствии явной записи выполнения, по доказательствам всех связанных `checks`. Явный `pending`, отзыв подтверждения или будущая дата выполнения не заменяются автоматическим выводом из других проверок. Связанные проверки должны быть актуальными и при явной записи: частичная сверка или прежняя версия креатива не завершают удалённое действие. Для ЕРИР требуется действительный совпадающий токен; два отсутствующих значения не являются подтверждением. Если проверки не связаны с действием, запиши его выполнение явно в `completed_events`.

Сохраняются UID и история выполнения; `changes.cancel` снимает только уведомление. Повторная сверка того же факта не переписывает исходные `completed_at` и `completion_source` уже сохранённого выполнения. Если само доказательство было ошибочным, явно исправь запись в `completed_events`, сохранив основание исправления в истории.

Список `checks` должен охватывать все проверки, названные в действии. Например, получение оплаты и проверка подписей требуют обеих связей, а не одной `payment`.

Действие экспортируется как `report-<id>` с постоянным UID; его указания и источник входят в JSON, Markdown и ICS. Скрипт не подтверждает действие и не устанавливает уведомления. Завершение записывай отдельно в `completed_events["report-<id>"]` с доказательством: подтверждение связанной проверки само по себе не удаляет организационное событие. Если проверка открылась заново, завершённое событие больше не покрывает её: сохрани прежнее выполнение в истории и явно возобнови действие со статусом `pending` в `completed_events` и актуальными указаниями. Не стирай факт прежнего выполнения и не считай старый результат подтверждением новой редакции.

## Публикация и завершение

Исполнителя каждого уже совершённого действия бери из источника: кто поставил пост в очередь, отправил документ или получил деньги. Роль рекламодателя не делает его автором всех действий сделки. Если источник не называет человека, фиксируй наблюдаемый результат без приписывания его стороне; не меняй автора действия при переносе в таблицу или историю.

Перед постановкой в отложенные проверь существующие записи: не создавать дубликат при сомнении, дошла ли первая попытка. Сохрани ID отложенной записи. Старый снимок до повторного создания не подтверждает отсутствие дубля сейчас. Авторизация на напоминания не равна авторизации на публикацию. Если условия не подтверждены, перечисли ближайшие незакрытые действия. Перенос предлагай при конкретном препятствии к согласованному сроку, а не автоматически из-за отсутствия будущей подписи/оплаты; не делай вывод «можно» из одного ERID.

Подтверждение очереди и его привязку к текущему размещению сохраняй по [правилам готовности](#готовность-к-публикации).

После выхода сохрани URL, фактическое время, скриншот поста и показатели в согласованные моменты (например, после 12 и 48 часов). Проверяй пометку, рекламодателя, ERID, текст, ссылки и медиа непосредственно в опубликованном сообщении. Выгрузку статистики и отправку документов выполняй в пределах поручения. УПД, завершённое размещение, отчёт в ОРД и обязательные отчисления — отдельные статусы. Не закрывай сделку только потому, что получены деньги или создан файл УПД.

## Проверка навыка

Полный набор автоматических проверок запускается из каталога навыка:

```sh
uv run --with lxml --with 'pypdf>=5,<7' --with 'pymupdf>=1.26,<2' --with 'markdown-it-py>=3,<5' python -m unittest discover -s tests -v
```

Поведенческие [сценарии](../tests/scenarios.md) проверяются отдельно; технические тесты не подтверждают факты конкретной сделки.
