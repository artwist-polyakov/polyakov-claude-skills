# Счёт и УПД

Скрипт самостоятельный: `docx-contracts`, Yii, база CRM и глобальное окружение Python не нужны. Шаблоны счёта, печатного УПД, каркас XML и официальная XSD находятся в `assets/accounting/`. Денежные расчёты выполняются через Decimal, НДС округляется по строкам до копеек. Рекламный сбор не прибавляется автоматически: его покрытие уже должно быть согласовано в цене и договоре.

## Команды

Запускать из каталога навыка. В ином каталоге указывать полный путь к скрипту.

```sh
uv run scripts/accounting.py invoice --data /path/to/accounting.json --output /path/to/deal/invoice-01.html
uv run scripts/accounting.py upd-print --data /path/to/accounting.json --output /path/to/deal/upd-01.html
uv run scripts/accounting.py upd-xml --data /path/to/accounting.json --output /path/to/deal/edo
# PDF — прямая печать созданного HTML, без сокращения формы:
uv run scripts/print_html.py --input /path/to/deal/invoice-01.html --output /path/to/deal/invoice-01.pdf
uv run scripts/print_html.py --input /path/to/deal/upd-01.html --output /path/to/deal/upd-01.pdf
```

`print_html.py` находит Chrome/Chromium/Edge, запускает отдельный временный профиль и печатает именно исходный HTML. При необходимости передать `--browser /путь/к/исполняемому/файлу` или `CHROME_BIN`. Если браузера нет, сохранить PDF через печать HTML в доступном браузере; не строить новую сокращённую таблицу через ReportLab, DOCX или другой макет. Счёт — A4 книжный, УПД — A4 альбомный. Рядом сохраняется `.pdf.source.json` с хешами HTML/PDF. Он подтверждает происхождение, но не заменяет просмотр каждой страницы. Проверить все 19 колонок УПД, обе стороны, КПП ЮЛ, Ф. И. О. подписанта, валюту, итог и строку 5б. Результат без графических подписей и печатей; у счёта по умолчанию нет даже пустой строки подписи, только имя ответственного. УПД содержит незаполненные строки подписей. Печатный УПД — собственная форма для услуг, согласованная сторонами; при НДС содержит реквизиты счёта-фактуры, в том числе строку 5б. В учётной политике/договоре согласовать применение этой формы.

Файлы создаются исключительно как новые: совпавший путь останавливает команду. Нельзя использовать УПД с будущей фиктивной датой: `services_performed=true` ставится только по подтверждённому оказанию услуги. Для предварительного обсуждения условий нужен договор, а не УПД о якобы выполненной работе.

Срок подготовки или отправки УПД согласуется отдельно от даты услуги. Установи действие, длительность, единицу и событие начала отсчёта. Если «через 48 часов после размещения» не уточняет начало или окончание услуги, в состоянии сделки оставь `closing_after_end_hours=null` и уточни начало отсчёта. Не превращай пример в автоматические 48 часов после окончания; до уточнения обозначь этот пробел в проекте условия и плане.

## Что собрать

Копировать `assets/accounting.example.json` в папку сделки и заполнить подтверждёнными данными. Недостающие обязательные сведения запросить до сборки. Файл с незаполненными полями не исполняется.

| Поле | Содержание |
|---|---|
| `document.number`, `date` | Номер конкретного счёта или УПД и дата `YYYY-MM-DD`. Для каждого вида документа отдельный файл данных/номер |
| `document.service_date` | Фактическое завершение услуг; нужно для УПД |
| `document.generated_at` | Реальное время создания XML со смещением, например `2026-10-17T12:00:00+03:00`. Дата документа от него независима |
| `contract.number`, `date` | Договор-основание |
| `seller`, `buyer` | `kind=ip` или `company`, полное имя, ИНН, адрес; КПП только ЮЛ; ИП — отдельные `fio.surname`, `name`, `patronymic` |
| `seller.ogrnip`, `buyer.ogrnip` и `ogrnip_date` соответствующей стороны | Для продавца-ИП с НДС в УПД обязательны номер и дата присвоения. В остальных случаях поля необязательны; любой заполненный номер проходит проверку контрольной цифры, дата — формата и календаря. В документ выводятся только переданные реквизиты |
| `seller.bank` | Для счёта: банк, БИК, расчётный и корреспондентский счета. Реквизиты не привязаны к бренду банка |
| `vat.rate` | Строка `none`, `5`, `7` или `22`; выбор подтверждается отдельно от налогового режима |
| `vat.price_mode` | `inclusive`: указанная цена единицы окончательная, НДС при его наличии выделяется из неё; `exclusive`: указана база, НДС при его наличии прибавляется сверху |
| `vat.exemption_basis` | При `none` — только подтверждённое основание освобождения. Слово «УСН» само по себе не является основанием |
| `items` | Одна или несколько услуг: описание с площадкой/периодом/ссылкой, количество, единица, код ОКЕИ, цена единицы. Числа задаются строками с точкой |
| `signer` | Ф. И. О., должность. Для XML `authority=self_ip` или `director` и подтверждённые полномочия |
| `had_advance` | Был ли аванс: явно `true` или `false`; для УПД |
| `payment_docs` | Реальные поступления: `[{"number":"123","date":"2026-10-19"}]`; при отсутствии `[]`. Номер счёта на оплату не является номером платёжного поручения |
| `advance_invoices` | При НДС и зачёте аванса: `[{"number":"А-1","date":"2026-10-19"}]`, необязательно `correction:{"number":"1","date":"2026-10-20"}` |
| `seller.edo_id`, `buyer.edo_id` | ID участника из карточки конкретной стороны у оператора. Исходящий титул всегда отправляет продавец покупателю; агент не выбирает направление вручную. ИНН/номер ящика не подменяют ID участника |
| `edo` | `operator` и `document_uuid`: UUID титула создаётся один раз и сохраняется при повторной сборке |
| `invoice_status` | Для счёта: `payable` по умолчанию; `paid_archive` — архивный экземпляр уже полностью оплаченного счёта, без нового требования оплаты |
| `payment_received` | При `paid_archive`: `{"amount":"50000.00","date":"2026-10-14"}`. Только подтверждённое поступление; сумма должна равняться полной сумме счёта |

`vat.rate` и `vat.price_mode` отвечают на разные вопросы. Освобождение от НДС (`rate=none`) не превращает окончательную цену в базу для надбавки. Если пользователь указал итоговую сумму без доплаты, сохраняй `price_mode=inclusive` и для освобождённого продавца. `exclusive` выбирается только когда исходная цена прямо задана без налога с начислением сверху. При `rate=none` суммы этих режимов совпадают, но смысл исходных условий всё равно нужно сохранить.

Ф. И. О., наименование, должность подписанта и номера документов переноси дословно из карточек. Номер бери целиком из источника; техническое имя каталога не является частью реквизитов. Не повышай «Директор» до «Генеральный директор», не заменяй кириллические буквы похожими латинскими. До выдачи сверяй эти значения в данных, HTML/PDF и XML с исходной карточкой; проверка XSD этого не доказывает.

В сопроводительном тексте называй результат точно: «проверены Ф. И. О., должность и строка подписанта», а не «проверена подпись». Напечатанное имя и пустая линия не являются подписью и не устанавливают дату подписания. Сформированный XML — неподписанный титул продавца; наличие сведений о подписанте не означает наличие электронной подписи.

В сопроводительном описании тоже различай строку 5 (платёжный документ из `payment_docs`) и строку 5б (авансовый счёт-фактура из `advance_invoices`). Правильный файл не исправляет неверное объяснение пользователю.

## Направление ЭДО

Сверять принадлежность ID с карточками сторон до генерации. Скрипт выводит продавца-отправителя и покупателя-получателя. В имени XML формат ФНС ставит **сначала получателя-покупателя, потом отправителя-продавца**. XSD не может определить, какой стороне на самом деле принадлежит ID.

Старые входы с `edo.sender_id`/`receiver_id` без ID у сторон останавливаются с объяснением миграции. Если старые поля оставлены вместе с новыми, скрипт проверяет их совпадение. Автоматически переносить их по названию нельзя: в старом файле они могли быть перепутаны. Переносить по исходным карточкам продавца и покупателя.

Для оплаченного счёта задавать `invoice_status=paid_archive` и `payment_received`. Генератор заменит требование оплаты архивной пометкой и не выведет устаревшие `payment_terms`. Это экземпляр ранее выданного счёта: сохранить его номер и дату; дата оплаты должна быть не раньше даты исходного счёта. Не создавать повторный долг и не менять даты ради проверки. При оплате до выставления счёта или частичной оплате этот узкий режим не подходит — оформить документы отдельно по согласованным данным.

## Выдача файлов

При сопровождении сделки соблюдай [порядок выдачи](handoff.md): до ответа зарегистрируй через `handoff.py register` каждый выдаваемый файл, включая HTML, PDF, XML и выдаваемые пользователю данные/манифесты. Сохрани факт выдачи старых версий отдельно от актуальности и проверь сохранённый ответ через `handoff.py check`. Контрольная сумма PDF в `.pdf.source.json` подтверждает происхождение печати, но не заменяет учёт выдачи самого PDF.

Для разовой бухгалтерской задачи без сопровождения сделки достаточно `handoff.py check-links --response /абсолютный/путь/ответ.txt` по [порядку проверки ссылок](handoff.md#заключительная-проверка). Эта команда не требует состояния сделки. Ни проверка XSD, ни просмотр PDF, ни регистрация выдачи не подтверждают подпись или приём документа оператором ЭДО.

## Профили и ограничения XML

- Только исходящий титул продавца по форме 5.03, XSD ФНС `ON_NSCHFDOPPR_1_997_01_05_03_05.xsd`; [источник и контрольная сумма](../assets/accounting/xsd/SOURCE.md).
- Только обычные услуги рекламы в рублях между российскими ИП/ЮЛ, выполненные в 2026 году. Один продавец, один покупатель, одна ставка НДС на документ.
- Цена без НДС в печатном и XML УПД должна воспроизводить сумму строки с округлением до копеек. Если для этого недостаточно 11 знаков после запятой, генератор останавливается: оформить УПД в учётной системе. Согласованные суммы не подгонять; счёт сохраняет исходную точность цены.
- Без НДС: функция **ДОП**, печатный статус 2. С НДС 5/7/22%: **СЧФДОП**, печатный статус 1. Налоговый режим не выбирает функцию автоматически.
- Подписывает сам ИП или руководитель ЮЛ, полномочия по сведениям электронной подписи (`СпосПодтПолном=1`). Представитель, МЧД, посреднические перевыставления, налоговый агент, иностранный участник, исправление, УКД, авансовый счёт-фактура, иные годы/ставки — за пределами профиля. Для них использовать учётную систему или кабинет оператора; не менять функцию вручную в XML.
- Зачёт ранее выставленных авансовых счетов-фактур поддержан: реквизиты помещаются в `СвСчФакт/ДопСвФХЖ1/СопрДокФХЖ`, `РеквНаимДок=АСЧФ`, исправление — в `РеквДопСведДок`. Сведения нужны для строки 5б. Сам авансовый счёт-фактура создаётся отдельно в учётной системе. Если при предоплате он не выставлялся на законном основании, текущий узкий профиль останавливается: оформить УПД с бухгалтером в учётной системе, не выдумывать реквизиты.
- В XML записывается Windows-1251, имя файла совпадает с `ИдФайл`. UUID сохраняется в данных соответствующего документа и, при сопровождении, в состоянии его сделки: повторная попытка не должна создавать другой документ. Для содержательного исправления после отправки пользоваться правилами исправления/аннулирования оператора.
- Перед записью обязательна проверка локальной XSD. Сеть для генерации не нужна после загрузки зависимостей `uv`. Встроенные в XSD расширения Schematron не исполняются; успешная XSD-проверка — только проверка структуры. Реальный импорт в Диадок/другой оператор, его дополнительные проверки, квалифицированная подпись и титул покупателя ещё впереди. Скрипт не проводит никаких действий в ЭДО и не утверждает, что документ принят.

Проверка контрольных цифр ИНН и формата банковских реквизитов не доказывает существование организации, владение счётом и полномочия подписанта. Эти сведения подтверждаются полученными реквизитами, выпиской и кабинетом выбранного оператора.
