# Договор и приложения

Основной пакет состоит из трёх самостоятельных файлов; для изменения подписанных условий есть отдельное дополнительное соглашение. Это позволяет менять условия одного размещения или очередную версию текста, не пересобирать подписанный договор и не затереть правки пользователя.

| Шаблон | Содержание | Когда готовить |
|---|---|---|
| `assets/templates/contract.docx` | Предмет, размещение, приёмка, маркировка, деньги, ответственность, обмен документами и двухколоночные реквизиты | После проверки сторон и выбора существенных условий |
| `assets/templates/placement-terms.docx` | Приложение № 1: площадка, формат, цена, дата, длительность, сроки материалов | Для каждого размещения |
| `assets/templates/creative.docx` | Приложение № 2: дословный пост, перечень медиа, таблица ссылок и маркировка | После согласования текста; окончательная версия — после получения erid |
| `assets/templates/amendment.docx` | Дополнительное соглашение: точные изменения, вступление в силу, обмен и отдельные даты подписей | При изменении уже подписанного условия |

Приложение № 1 — техническое задание, № 2 — фиксация креатива. Они не являются автоматически дополнительными соглашениями. Если меняется уже подписанное условие договора или приложения, согласовать отдельное изменение с номером и датой; не подменять подписанный файл новой сборкой.

При поручении подготовить пакет и наличии согласованного исходного текста выпускай **проект** Приложения № 2, даже если ERID или полная карточка ОРД ещё проверяются. В `POST_TEXT` — точный исходник с прежней строкой маркировки, в служебном разделе — «идентификатор и соответствие ОРД не подтверждены; до сверки не использовать для публикации». Не называй исходную строку ошибочной или отозванной без доказательства. Не вырезай ERID из поста и не подменяй его альтернативным кодом. Когда данных достаточно для проекта, формулировка «приложение не выпускаю до токена» необоснованно оставляет поручение незавершённым. Окончательный статус документа и готовность публикации проверяются отдельно.

## Что сохранено из исходников

Структура разделов и нумерация договора, формулировки о предмете, согласовании текста, смысле «топа», подтверждении размещения, моменте оплаты, сроке действия; геометрия страницы, Montserrat 11 pt, жирные заголовки и две колонки реквизитов. В Приложении № 2 сохранена исходная трёхколоночная таблица ссылок. Переменные коммерческие и спорные правовые положения вынесены в явные поля.

Преднамеренные изменения вёрстки: приложения выделены в отдельные файлы, убраны пустые абзацы для ручной подгонки, город и дата разделены табуляцией. Реквизиты начинаются с отдельной страницы: слева Исполнитель, справа Заказчик; для каждого блока сохранена целостность. Высота строки таблицы ссылок не фиксируется, заголовок повторяется при переносе. Шрифт не уменьшается под длинный текст.

В DOCX встроены Montserrat Regular и Bold, поэтому не требуется системная установка. Источник — [официальный репозиторий Montserrat](https://github.com/JulietaUla/Montserrat/tree/master/fonts/ttf), лицензия — `assets/templates/Montserrat-OFL.txt`. Другие начертания исходные шаблоны не используют. Системы, не поддерживающие встроенные шрифты, требуют установленный Montserrat и отдельную проверку отображения.

Имена, реквизиты, адреса, ссылки, токен, текст прежней рекламы, внешние связи и личные метаданные исходной сделки удалены. Частные исходники не входят в навык.

## Карта полей и подготовка данных

Полный перечень находится в `assets/template-fields.json`: для каждого поля есть вопрос, пример, примечание и список документов. Примеры демонстрационные; их нельзя выдавать за сведения о реальной сделке. Цены, сроки и условия из примера не являются настройками по умолчанию.

`fields.json` — плоский объект, все значения строки. Имена строго `UPPER_SNAKE_CASE`. Например:

```json
{
  "CONTRACT_NUMBER": "Р-2026-001",
  "CONTRACT_DATE": "«20» октября 2026 г.",
  "CHANNEL_NAME": "Название согласованной рекламной площадки",
  "CHANNEL_URL": "https://example.org/community"
}
```

`CHANNEL_NAME` и `CHANNEL_URL` задают любую рекламную площадку: канал, сообщество, сайт и т. п. В договоре она далее называется «Канал». Для площадки без ленты или топа отдельно согласуй и адресно замени соответствующие условия размещения в договоре и Приложении № 1. Универсальное название площадки не заменяет проверку правил её работы; порядок сопровождения в навыке пока рассчитан на Telegram.

В `CONTRACTOR_PARTY` и `CUSTOMER_PARTY` передавать описание стороны до обозначения её роли включительно. Связки «с одной стороны», «с другой стороны» и соединительные фразы уже находятся в шаблоне. В `AMENDMENT_CHANGES` не повторять внешний номер «1.»: его добавляет шаблон; номера изменяемых пунктов договора сохраняются внутри текста.

Это фрагмент формы, а не полный набор для сборки. Не спрашивать каждое поле по отдельности: сначала извлечь достоверные данные из карточек сторон, переписки и состояния сделки; затем задать только оставшиеся вопросы блоками.

| Блок | Поля и источник |
|---|---|
| Стороны и полномочия | `CONTRACTOR_PARTY`, `CUSTOMER_PARTY` — полное вступление с ролью и полномочиями; `CONTRACTOR_*`, `CUSTOMER_*` — реквизиты проверенных карточек. Заказчик может быть агентом, а не рекламодателем |
| Документ | `CONTRACT_NUMBER`, `CONTRACT_DATE`, `CONTRACT_CITY`; дата документа берётся из согласования или полученного договора, фактические даты подписания фиксируются отдельно |
| Размещение | `CHANNEL_NAME`, `CHANNEL_URL`, `PLACEMENT_FORMAT`, `PRODUCT_NAME`, `PRODUCT_URL`, `PUBLICATION_DATETIME`, `FEED_HOURS`, `TOP_HOURS`, `MATERIALS_CLAUSE` — согласованные условия |
| Деньги | `PRICE_TOTAL`, `VAT_CLAUSE`, `AD_FEE_CLAUSE`, `PAYMENT_CLAUSE` — итог к оплате, режим НДС и основание, распределение расходов, сроки |
| Маркировка | `MARKING_DUTIES_CLAUSE`, `REPORTING_DUTIES_CLAUSE`, `MARKING_DISPLAY_CLAUSE`, `CREATIVE_MARKING_CLAUSE`, `MARKING_PARTY`, `ERID`, `ERID_PLACEMENT` — выбранный участник, конкретные обязанности и подтверждения |
| Креатив | `POST_TEXT`, `MEDIA_MANIFEST`, `LINK_COUNT`, пары `LINK_1_ANCHOR`/`LINK_1_URL` и далее — дословно одобренная версия |
| Исполнение и документы | `PUBLICATION_CONDITIONS_CLAUSE`, `LINK_AFTER_PUBLICATION_HOURS`, `CUSTOMER_CONTACT`, `CLAIMS_DEADLINE`, `CONTRACTOR_CLAIMS_CONTACT`, `CLAIMS_EVIDENCE_REQUIREMENTS`, `ACCEPTANCE_CLAUSE`, `METRICS_CLAUSE`, `EXCHANGE_METHOD`, `CLOSING_DOCUMENTS_CLAUSE`, `EXCHANGE_CLAUSE` |
| Защита стороны | `EDITING_CLAUSE`, `TAKEDOWN_CLAUSE`, `CUSTOMER_RESPONSIBILITY_CLAUSE`, `WARRANTIES_CLAUSE`, `INDEMNITY_CLAUSE`, `LIABILITY_CLAUSE`, `LATE_PAYMENT_CLAUSE`, `FORCE_MAJEURE_CLAUSE`, `DISPUTES_CLAUSE` |

`MARKING_PARTY` называет ответственного за регистрацию и предоставление подтверждения выдачи токена. Имя ответственного не подтверждает выполненную регистрацию: выдачу токена и сверку зарегистрированного материала проверяй отдельно, в том числе когда приложение собирается до регистрации.

Все поля выбранного шаблона обязательны (для сканов два пункта создаются из `--exchange-file`), кроме разрешённого неизвестного контакта Исполнителя для претензий, описанного ниже. «Опциональный пункт» означает выбор его содержания, а не молчаливое исключение: например, при отсутствии неустойки написать «Договорная неустойка за просрочку оплаты не установлена». Номер пункта уже находится в шаблоне; в `*_CLAUSE` передавать полный согласованный текст без номера.

### Претензии к размещению

В собственном шаблоне договора роли в п. 3.3 закреплены непосредственно в тексте: **Заказчик направляет Исполнителю** претензии к качеству и объёму услуг. Они не меняются от роли пользователя: даже когда агент представляет рекламодателя, адресатом такой претензии остаётся Исполнитель.

```json
{
  "CLAIMS_DEADLINE": "в течение трёх рабочих дней после получения отчёта",
  "CONTRACTOR_CLAIMS_CONTACT": "",
  "CLAIMS_EVIDENCE_REQUIREMENTS": "описание нарушения; подтверждающие материалы при их наличии"
}
```

Это только фрагмент карты и пример для согласования, а не срок по умолчанию. `CLAIMS_DEADLINE` содержит срок с предлогом и точным событием начала отсчёта. Не заменяй рабочие дни часами, получение отчёта окончанием размещения или неизвестный срок примером 24 часа. Для неизвестного срока используй `[УТОЧНИТЬ СРОК И НАЧАЛО ОТСЧЁТА]`.

`CONTRACTOR_CLAIMS_CONTACT` заполняется подтверждённым адресом или каналом **Исполнителя** с учётом согласованного способа обмена. `CUSTOMER_CONTACT` служит другому направлению: ссылкам, снимкам и уведомлениям **Заказчику**. Если контакт Исполнителя неизвестен, оставь пустую строку или не передавай поле: собственный шаблон покажет `[УТОЧНИТЬ ПОДТВЕРЖДЁННЫЙ КОНТАКТ ИСПОЛНИТЕЛЯ]`. Подстановка контакта заказчика вместо него запрещена. После готовой метки «Контакт Исполнителя:» укажи только канал и значение, без повторения «Почта/Контакт Исполнителя». Программа не устанавливает принадлежность аккаунта; её нужно подтвердить по источнику.

Неизвестный адрес регистрации помещай в поле адреса стороны. Он не относится к `CUSTOMER_CONTACT` и не мешает использовать подтверждённый Telegram-контакт. Вводная часть `*_PARTY` заканчивается ролью стороны без точки: запятая и продолжение уже есть в шаблоне. Дополнительные сведения о конечном рекламодателе внеси в соответствующее условие, а не после законченного предложения внутри вводной.

`CLAIMS_EVIDENCE_REQUIREMENTS` — только требования к содержанию и подтверждениям претензии после готовой метки. Не добавляй в эти три вставки заново отправителя, адресата или весь пункт. Завершающие точки уже находятся в шаблоне.

Прежний свободный `CLAIMS_CLAUSE` отклоняется при сборке собственного договора, даже если новые поля тоже переданы. Перенеси его согласованный срок и требования в новые поля, отдельно установи контакт Исполнителя и сохрани новую карту. Ручные правки и полученные договоры не пересобирай ради новой схемы: используй адресную правку новым файлом через `--patch` и проверку SHA. Для пользовательских шаблонов собственная формулировка автоматически не навязывается.

`LINK_AFTER_PUBLICATION_HOURS` заполняет пункт 3.1 собственного договора: через сколько часов **после публикации** Исполнитель должен отправить **Заказчику ссылку на пост и снимок экрана**. Вставляется только неотрицательное число часов, включая дробное с точкой или запятой, без слов и единиц; действие и начало отсчёта уже заданы шаблоном. Если срок не согласован, вставь `____` и оставь `schedule.link_after_publication_hours=null`. Не подставляй срок из примера или срок уведомления о другом событии. Подтверждённое значение переносится в новую версию через `--revise` с этим же именем поля.

Старое имя `NOTICE_HOURS` явно отклоняется, даже если передано вместе с новым. Для новой сборки создай отдельную карту, перенеси подтверждённое число в `LINK_AFTER_PUBLICATION_HOURS` и удали старое имя. Старые результаты и их карты не переписывай: замена шаблонного поля изменила SHA шаблона, поэтому старый DOCX не следует автоматически пересобирать через `--revise`. Согласованную правку прежнего или вручную изменённого документа внеси адресно в новый файл через `--patch` с проверкой SHA; ограничение числового поля не распространяется на полный текст такой правки.

Срок закрывающих документов не берётся из примера: нужны ответственный, вид документа, длительность и точное событие начала отсчёта. Если начало срока неизвестно, оставь явное место для согласования. При сканах эти сведения передаются в `--exchange-file`, при других способах — в `CLOSING_DOCUMENTS_CLAUSE`.

`render_contract.py` останавливает сборку и называет поле, если на границе подстановки и шаблона повторяется одинаковый знак `.`, `,`, `;` или `:`. Например, если после `{{MARKING_PARTY}}` в шаблоне уже стоит точка, значение `Заказчик.` нужно исправить на `Заказчик`. Значение не исправляется молча: сохрани новую карту полей и повтори сборку. В `MEDIA_MANIFEST` передавай только содержимое после готовой метки «Медиа:»: `отсутствуют.` или перечень файлов, без повторного «Медиа».

Эта проверка не чистит текст целиком: `POST_TEXT` и поля `*_URL` исключены, пунктуация внутри значения не меняется. Не удаляй точки, двоеточия, пробелы или части адресов из утверждённого поста и URL ради успешной сборки. Остальные неудачные стыки, например «.;», и повторные вводные слова проверь чтением готового документа; исправляй соответствующее служебное поле, сохраняя смысл согласованного условия.

При НДС явно установить: режим продавца, наличие освобождения и основание, ставку, сумму налога, цену без налога и итог. `VAT_CLAUSE` — итоговое предложение договора; его получают из проверенных налоговых данных, а не из признака «УСН». Для общей ставки пример: «В указанную стоимость включён НДС по ставке 22 % в сумме … рублей». Ставка и сумма требуют проверки на дату операции. Никакой автоматической привязки ОСНО/УСН к ставке в генераторе нет.

Согласованный итог к оплате не становится неизвестным из-за неподтверждённого статуса НДС. Если стороны уже установили окончательную цену без надбавки, сохрани это во всех версиях договора и приложений. В `VAT_CLAUSE` можно написать: «Указанная цена является окончательной; НДС, если он подлежит предъявлению, выделяется из неё. До подписания подтвердить ставку и сумму НДС либо основание освобождения». Это не подтверждает саму обязанность платить НДС. Не оставляй прежнюю заглушку «включение НДС в цену не подтверждено» после согласования такого итога.

`AD_FEE_CLAUSE` отдельно описывает законного плательщика и экономическое возмещение. Варианты: расходы включены в цену; отдельная согласованная компенсация с расчётом и сроком; другая подтверждённая схема цепочки. Фраза «платит заказчик» сама по себе не меняет установленную законом обязанность. См. [правовой справочник](legal.md).

В служебном поле `ERID` проекта ТЗ или Приложения №2 до проверки укажи «НЕ ПОДТВЕРЖДЁН» и точное известное основание ожидания; согласованный срок предоставления добавляй только при его наличии. Не приписывай кандидатам выдачу или отмену. Это служебное поле не меняет строку ERID внутри дословного `POST_TEXT`. В окончательном приложении с креативом нужен выданный ОРД идентификатор, совпадающий с маркировкой поста; технический генератор не подтверждает его существование и соответствие креативу.

`ACCEPTANCE_CLAUSE` — целый пункт о приёмке услуги, а не вставка в фразу «Исполнитель направляет…». Если порядок приёмки ещё не выбран, возьми `unknown_value` из карты полей. Условия отправки ссылки/снимка и закрывающих документов находятся в своих пунктах; не собирай их повторно из обрывков предложений. Перед выдачей прочитай полные составленные пункты в окончательном DOCX: техническая сборка не проверяет грамматику и смысл свободного текста.


## Обмен сканами из единого источника

В собственном `contract` обязательно управляющее поле `EXCHANGE_METHOD`: `scans`, `edo`, `paper` или `unknown`. Поле не печатается в документе. **Временные сканы до восстановления основного ЭДО тоже означают `scans`.** `unknown` допустим, только если пользователь ещё не выбрал способ. Другие способы и сторонние шаблоны сохраняют заполнение полных пунктов; генератор не угадывает способ из свободного текста.

Для `scans` создай отдельный `exchange-v1.json` по `assets/exchange.example.json` и передай `--exchange-file`. Оба поля `EXCHANGE_CLAUSE` и `CLOSING_DOCUMENTS_CLAUSE` из ручной карты убери: их формирует генератор. Совпадающие значения допустимы, противоречащие вызывают отказ до записи DOCX. Одна общая часть с каналом, контактами, статусом согласования и последующим обменом входит в оба пункта, включая закрывающие документы.

| Поле JSON | Значение |
|---|---|
| `channel` | `telegram`, `email`, `other` или `unknown`; уже выбранную переписку не объявляй неизвестной |
| `channel_name` | Название только для `other`; иначе `null` |
| `contractor_contact`, `customer_contact` | Контакты только в выбранном канале или `null`. Telegram: `@username`, `https://t.me/username` либо международный номер. Email не подставляется в Telegram. При `unknown` оба контакта — `null` |
| `agreement` | `proposed` — предложено, согласие контрагента не подтверждено; `agreed` — есть согласование обеих сторон; `unknown` — статус неизвестен. Ни один статус не подтверждает подписания |
| `closing_document` | Название закрывающего документа либо `null` |
| `closing_sender` | `contractor`, `customer` либо `unknown` |
| `closing_deadline` | Только точный срок с единицей и началом отсчёта, например «в течение согласованного числа часов после окончания размещения»; фактическое число возьми из согласования. Без контактов и порядка обмена, без конечной точки. Если срок неоднозначен — `null` |
| `followup_method` | `edo` — последующее ЭДО; `paper` — бумажные оригиналы; `none` — последующий обмен не нужен; `unknown` — не согласован. Ни один способ не назначается по умолчанию |
| `followup_deadline` | Согласованный срок/событие последующего обмена без конечной точки либо `null`. При `none`/`unknown` только `null`; для `edo`/`paper` неизвестный срок остаётся явным местом уточнения |

Все ключи обязательны, неизвестные значения — `null` или соответствующий `unknown`. Пример — форма для заполнения, не источник фактов. Неизвестный контакт выводится как место уточнения **в выбранном канале**; согласование порядка учитывается отдельно. Если пользователь выбрал Telegram, но его аккаунт не указан, это не повод заменить канал почтой или предложить смешанный обмен. Генератор проверяет структуру и синтаксис контактов, но их принадлежность, фактическое согласование и смысл свободного срока агент сверяет с источниками.

```sh
uv run scripts/render_contract.py --template contract --fields /путь/fields.json --exchange-file /путь/exchange-v1.json --output /путь/договор-v1.docx
uv run scripts/render_contract.py --revise /путь/договор-v1.docx --fields /путь/changed-fields.json --exchange-file /путь/exchange-v2.json --output /путь/договор-v2.docx
```

`.fields.json` сохраняет `exchange_source` с путём и SHA. Без нового `--exchange-file` команда `--revise` повторно использует неизменный исходник; изменение его байтов останавливает сборку. Для изменения канала, контакта, согласования или сроков сохрани новый JSON и передай его явно: оба пункта обновятся вместе. Не дописывай ручные формулировки пунктов к новому источнику. При переходе со сканов на иной способ передай новый `EXCHANGE_METHOD` и обе новые clause без `--exchange-file`. Старые файлы сохраняются; правки человека запрещают пересборку и требуют адресного `--patch` с проверкой SHA. `--patch` не принимает `--exchange-file`: в таком документе точные согласованные изменения вносятся в оба относящихся к обмену пункта с последующим чтением и проверкой вёрстки.

## Выбор положений в интересах пользователя

Не выдавать примерные пункты из карты за универсально лучший договор.

Согласованные дату, цену и сроки сохраняй. Новые обязательства, отказ от выгодного пользователю условия и изменение способа обмена выделяй как предложения с кратким объяснением. Например, срок отправки бумажных оригиналов из примера не становится условием сделки только потому, что выбран обмен сканами. Более поздняя подпись сама по себе не основание переписывать заданную дату документа и ссылки на него в приложениях.

- **Площадка / блогер:** предоплата и право переноса при задержке; точное время в ленте и топе; отсутствие несогласованных гарантий просмотров; заверения о продукте и правах; подтверждения регистрации; обусловленное нарушением возмещение расходов; ограничение ответственности в допустимых законом пределах.
- **Рекламодатель:** запрет несогласованных правок; подтверждение сроков и маркировки; понятный возврат за неоказанное; разумный срок замечаний; KPI и компенсация только если согласованы; достаточная ответственность площадки и доступ к подтверждениям размещения.
- **Агент:** назвать рекламодателя отдельно; проверить полномочия, принципала и цепочку договоров; распределить подготовку текста, регистрацию, сведения и первичные документы; избежать обещаний за участников, которыми агент не управляет. Этот пакет оформляет размещение, а не заменяет агентский договор с принципалом.

В обоих направлениях сверять пункты между собой: предоплата и условия публикации; срок размещения и приёмка; компенсация сбора и итоговая цена; маркирующий участник и обязанности Заказчика; обмен сканами и отправка первички. Публично-правовая ответственность не переносится одним пунктом договора.

В каждом новом пункте прочитай вслух связку «кто — что вправе или обязан сделать — при каком условии». Право блогера запросить доказательства не должно случайно зависеть от запроса самого рекламодателя. В пояснениях НДС относится к продавцу услуг; сверь названия сторон с договором.

Если пользователь требует подписания до оплаты, в `PAYMENT_CLAUSE` явно свяжи возникновение обязанности оплатить с подписанием необходимых документов требуемыми сторонами. Крайний срок предоплаты укажи отдельно, в согласованной точности. После сборки прочитай сам платёжный пункт и связанные положения приложения: фразы «100 % предоплата» недостаточно для сохранения порядка «подписи → оплата». Если сроки несовместимы, выдели конкретное расхождение для согласования. При получении чужой редакции сначала составь [таблицу сверки](contract-review.md).

В собственном проекте согласуй последствия задержки между платёжным пунктом и условиями выхода. Если новую дату стороны выбирают совместно, формулируй право Исполнителя приостановить выход до выполнения условий и отдельно — согласование новой даты. Фраза «вправе перенести» без этого уточнения может противоречить соседнему пункту о взаимном согласовании. При проверке чужой редакции сохрани её конкретный объём защиты пользователя и объясни предлагаемое уточнение; не подменяй согласованное условие автоматически.

Для сканов в обоих пунктах используется одна общая часть из `--exchange-file`. Неизвестный аккаунт и отсутствие согласия контрагента не отменяют уже выбранный пользователем канал; вносить эти сведения нужно в разные поля JSON, а не пересказывать два пункта вручную.

## Сборка без docx-contracts

Из каталога навыка:

```sh
uv run scripts/render_contract.py --template contract --list-fields
uv run scripts/render_contract.py --template contract --fields /путь/fields.json --output /путь/договор-v1.docx
uv run scripts/render_contract.py --template placement-terms --fields /путь/fields.json --output /путь/приложение-1-v1.docx
uv run scripts/render_contract.py --template creative --fields /путь/fields.json --post-file /путь/approved-post.txt --links-file /путь/post-links.json --output /путь/приложение-2-v1.docx
uv run scripts/render_contract.py --template amendment --review /путь/review-v1 --fields /путь/amendment-fields.json --output /путь/допсоглашение-v1.docx
```

Python 3.11+, `uv` устанавливает объявленные зависимости. Подстановка OOXML использует стандартную библиотеку; связь допсоглашения со сверкой PDF использует `pypdf`. Нет `docxtpl`, Word, LibreOffice или `docx-contracts` как зависимости **генерации**. Для просмотра нужен редактор DOCX или отдельное преобразование в PDF/изображения.

Для допсоглашения по полученной редакции передай `--review`: точное `AMENDMENT_CHANGES` будет создано из единого набора решений, несовпадающий ручной текст отклоняется. Сохраняй карту полей рядом с DOCX, регистрируй вид `amendment`, PDF связывай через `--source-docx` по [порядку выдачи](handoff.md). Для самостоятельного соглашения без сверки полученного пакета допустим обычный вызов без `--review` с подтверждённым перечнем изменений.

Можно передать путь к вручную отредактированной копии шаблона в `--template`. Сохраняются стили, свойства абзацев и текстовых фрагментов, секции и неизменённые части ZIP. Разрывы строки `\n` превращаются в разрывы строки Word. Ссылки вставляются в таблицу как точные текстовые адреса, без старых скрытых гиперссылок.

В приложении с креативом `LINK_COUNT` — строка с числом от 0 до 999. Для каждого номера нужны обе строки `LINK_<номер>_ANCHOR` и `LINK_<номер>_URL`. При нуле строка данных удаляется; для подтверждённого отсутствия ссылок это допустимо. Таблица не ограничена шестью строками исходного примера. Разметка Markdown/HTML не преобразуется; в `POST_TEXT` нужен дословный текст, а форматирование и медиа сверяются с утверждённым оригиналом отдельно.

При наличии исходника поста обязательно передай `--post-file`. Если `POST_TEXT` отсутствует в карте, значение берётся из файла; если присутствует, должно совпасть с ним дословно. Удалённый ERID или очищенный пробел остановит сборку. Рядом с DOCX сохраняются путь и SHA-256 исходника; `--revise` проверяет эту привязку и не принимает изменённый текст без нового явно переданного исходника. Исходный файл и карта сохраняют CRLF/LF; в Word оба вида перевода строки отображаются одним разрывом. Подготовка новой версии не означает её согласования.

Пока факт выхода не подтверждён, называй текст «согласованным» или «подготовленным», а не «опубликованным». В `MEDIA_MANIFEST` укажи только содержимое: «отсутствуют» или перечень файлов. Метка «Медиа:» уже есть в шаблоне; генератор отвергает её повтор.

Без `--force` существующий результат не перезаписывается. Сам шаблон не перезаписывается даже с этим флагом. `--force` применяется только по явной просьбе пользователя; обычно новая редакция получает `v2`, `v3` и далее. После ручных правок пользователя сравнить версии и изменить нужный файл адресно, а не воспроизвести его из устаревших данных.

## Последующие правки без потери вёрстки

Не заменять `paragraph.text`, `cell.text`, содержимое `w:p` или все его `w:r` заново и не пересобирать DOCX через HTML/`textutil`: так теряется Montserrat, жирность и форматирование. Для созданных этим навыком документов есть два поддержанных пути.

**Исходник не меняли вручную.** При первой сборке рядом автоматически сохраняется полная карта `имя.docx.fields.json`: все значения, путь и контрольная сумма шаблона, контрольная сумма результата. Для следующей версии передать только изменения:

```sh
uv run scripts/render_contract.py --revise /путь/договор-v1.docx --fields /путь/changed-fields.json --output /путь/договор-v2.docx
```

После любых правок отрисуй окончательный DOCX через `render_docx.py render`, просмотри все PNG и отдельно запиши результат `confirm`; прежний просмотр к новой версии не относится. [Порядок проверки вёрстки и регистрации](handoff.md#проверка-вёрстки-docx).

Команда объединяет изменения с полной сохранённой картой. Если человек изменил DOCX или сам шаблон, пересборка останавливается. Не исправлять контрольную сумму в карте, чтобы обойти эту проверку. Путь к шаблону в карте относится к тому каталогу, где собиралась версия; перенос папки не даёт основания переписать документ заново.

**В готовом DOCX есть ручные правки либо сохранённой карты нет.** Вначале получить контрольную сумму и список всех абзацев, включая ячейки таблиц:

```sh
uv run scripts/render_contract.py --input /путь/договор-v1.docx --inspect > /путь/paragraphs.json
```

Подготовить `patch.json`, взяв `source_sha256` из этого вывода. `find` — дословный фрагмент исходной версии, включая переводы строк. Пример структуры:

```json
{
  "source_sha256": "контрольная сумма из --inspect",
  "replacements": [
    {
      "find": "старый точный текст",
      "replace": "новая согласованная редакция"
    },
    {
      "part": "word/document.xml",
      "paragraph": 27,
      "find": "https://example.org/old",
      "replace": "https://example.org/new"
    }
  ]
}
```

Затем:

```sh
uv run scripts/render_contract.py --input /путь/договор-v1.docx --patch /путь/patch.json --output /путь/договор-v2.docx
uv run scripts/render_contract.py --input /путь/договор-v2.docx --audit
```

Замены выполняются последовательно в выбранной части, по умолчанию `word/document.xml`. Без номера абзаца фрагмент должен встретиться во всей части ровно один раз. Номер из `--inspect` сужает поиск для повторяющихся URL или одинаковых ячеек. Неоднозначная, отсутствующая замена или несовпадающий SHA не создаёт результата. Фрагмент не может пересекать границу абзацев; перевод строки внутри одного абзаца поддерживается. Новая строка наследует свойства первого заменяемого текстового фрагмента; свойства абзаца, секции и остальных фрагментов сохраняются. Активные гиперссылки и поля Word требуют отдельной правки связи и здесь отвергаются; в таблицах наших шаблонов URL хранится точным текстом.

Результат адресной правки всегда новый файл; `--force` запрещён. Такая версия дальше правится адресно: устаревшая карта исходной сборки не применяется. Для уже подписанного пакета сначала определить с пользователем, нужна новая редакция или отдельное соглашение. Копия или дополнительное соглашение не становится подписанным из-за наличия подписей в прежнем файле.

`--audit` требует явный Montserrat для обычного текста и Noto Emoji для эмодзи; ненулевой код завершения означает ошибку оформления. Это намеренно строгая проверка шаблонов навыка, а не универсальный анализ наследуемых стилей любых сторонних DOCX. Адресная правка проверяет шрифты до и после изменения и останавливается, если исходник уже потерял оформление. Не выдавать такой файл как исправленный; выбрать сохранённую целую версию либо восстановить стиль адресно с отдельной проверкой.

## Эмодзи и точность текста

При сборке и адресной правке символы получают встроенный монохромный Noto Emoji, а обычный текст остаётся Montserrat. Строка поста, порядок Unicode, переводы строк, ERID и URL не переписываются. В печатном приложении эмодзи чёрно-белые; вид публикации Telegram остаётся отдельным оригиналом креатива.

Шрифт поставляется в `assets/templates/NotoEmoji.ttf`, лицензия OFL — рядом. Источник: [официальные файлы Noto Emoji](https://github.com/google/fonts/tree/main/ofl/notoemoji). Сборка не требует сети или установки шрифта. Если шрифт не содержит символ, скрипт сообщает об этом и не создаёт DOCX; удалять или заменять символ в одобренном посте нельзя. Встраивание и успешный `--audit` не доказывают, что конкретный просмотрщик показал каждый символ: после преобразования проверить текст PDF и изображения всех страниц, включая эмодзи. Недоступное преобразование или пропавший символ фиксируется как незавершённая визуальная проверка, а не успешная выдача.

## Проверка перед выдачей

1. Сверить реквизиты и полномочия обеих сторон, номер/дату во всех трёх файлах, суммы и налоговую формулировку со счётом.
2. Сверить имена маркирующих участников, erid, буквальный текст, ссылки и список медиа с одобренной версией.
3. Прочитать документ целиком, в том числе неизменяемый генератором пункт 5.3 и выбранные положения о правках и удалении: подходят ли они выбранной стороне и фактической схеме.
4. Выполнить `--input готовый.docx --audit`, затем отрисовать каждый окончательный DOCX через `render_docx.py render`, осмотреть все PNG и записать результат через `confirm` по [порядку проверки вёрстки](handoff.md#проверка-вёрстки-docx). Особое внимание — длинным юридическим положениям, адресам в колонках, таблице ссылок и переносу подписей. Без отрисовки или при `needs_changes` не выдавать документ как готовый; назвать конкретное препятствие. Любая последующая правка требует новой проверки, даже если PDF остаётся внутренним.
5. По [порядку выдачи](handoff.md) зарегистрировать через `handoff.py register` каждый выдаваемый файл, включая PDF-превью, с версией и контрольной суммой. Факт прежней выдачи сохранять отдельно от актуальности; старый выданный документ не становится внутренним черновиком после замены. Перед ответом выполнить `handoff.py check` для сохранённого текста ответа и исправить ошибки ссылок/реестра.
6. Проверить точность описания результата: напечатанное Ф. И. О. и пустая линия — реквизиты строки подписанта, а не проверенная подпись. Они не подтверждают подписания или его даты. Сборка файла и запись в реестре не означают подписание, регистрацию в ОРД или отправку контрагенту. Отдельные учебные бухгалтерские ветки хранить отдельно, не меняя документы, состояние и реестр основной сделки.

Автоматическая проверка:

```sh
uv run --no-project python -m unittest discover -s tests -p test_contract.py -v
```

Тесты проверяют заполнение четырёх шаблонов, адресную правку готовой версии, отказ неоднозначных замен и пересборки после ручных правок, точное сохранение эмодзи и встроенного шрифта, сохранение колонок и шрифтов, целостность OOXML, таблицу произвольной длины, разбитые между фрагментами маркеры, многострочные значения, отсутствие незаполненных полей и защиту от перезаписи. Они не заменяют проверку правовых фактов, арифметики сделки и каждой страницы результата.

Перед выдачей прочитай стыки подстановок: не должно быть повторных точек, вводных слов и противоречивых подписей вроде «Регистрацию выполнил: не подтверждено». Неизвестного исполнителя регистрации обозначай неизвестным. Исправляй карту полей или служебную формулировку новой версией; дословный утверждённый пост ради такой правки не меняй.

### Проверка адресов перехода

После создания или получения приложения с постом выполни `uv run scripts/inspect_links.py --input FILE --expected LINK_MAP.json --output NEW_REPORT.json`. В `LINK_MAP.json` передай ту же исходную карту заказчика, которая использована в `import-creative --links` и `render_contract.py --links-file`; отдельный список URL вручную не составляй. Отчёт читает именно ссылки PDF/DOCX, а не только напечатанные адреса; документы и исходная карта не изменяются. Сохрани отчёт среди свидетельств проверки.

Для PDF сверяй страницу и прямоугольник аннотации с видимым якорем на отрисованной странице; для DOCX отчёт содержит якорь и адрес связи. Проверь каждое отличие счётчиков. Например, ссылка на цену встречается дважды вместо одного раза, а ссылка на продукт — реже: это может означать, что якорь продукта ведёт к цене. Установи фактическое назначение каждого якоря, не объявляй ошибкой только число аннотаций. Таблица адресов, переносы ссылок и обычный некликабельный текст могут менять число переходов. Замечание к чужому исходнику и проект исправления храни отдельно от неизменного оригинала.

Перед выдачей каждый текущий DOCX/PDF приложения, включая собственный проект и его PDF, должен иметь отдельный зарегистрированный отчёт со сравнением с картой текущей сделки. Для объяснённых различий и предупреждений сохрани явное решение `resolution` со ссылкой на зарегистрированную сверку по [порядку выдачи](handoff.md); отчёт без `--expected` эту проверку не проходит.

Поле PDF `anchor_hint` показывает текст из области той же аннотации рядом с `target`. Это подсказка для чтения: область иногда захватывает соседнюю строку, а у скана текстового слоя может не быть. Сопоставь её с изображением страницы; пустое поле не означает отсутствия ссылки. Извлечение использует [PyMuPDF Page.get_textbox](https://pymupdf.readthedocs.io/en/latest/page.html#Page.get_textbox), зависимость устанавливается через `uv` из заголовка скрипта. Для входящего приложения проверяй сам оригинал и регистрируй отдельный отчёт по [порядку выдачи](handoff.md), даже если собственное приложение уже прошло проверку.


Для приложения с креативом передавай исходную JSON-карту в `--links-file` вместе с `--post-file`. Не переписывай `LINK_<N>_ANCHOR/URL` из памяти: генератор читает ту же карту, что `deal.py import-creative --links`, и сам заполняет поля с исходными якорями, порядком, повторами и параметрами. В ручной карте полей их можно опустить; совпадающие значения допустимы, противоречащие и лишние строки вызывают отказ до записи DOCX. Форматы карты описаны в [порядке работы](workflow.md). Список URL без якорей остаётся допустимым исходником, но не подменяет полученную таблицу с якорями.

Источник сохраняется в `links_source` рядом с `post_source` в `.fields.json`. При `--revise` исходная карта используется повторно и проверяется; ручная замена одного `LINK_*` при прежней карте не проходит. Если карта действительно изменилась, сохрани новый исходный файл и явно передай новый `--links-file` для отдельной версии. Согласование и проверку ОРД обнови для новой версии креатива.
